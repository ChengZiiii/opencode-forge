## Context

**宿主这一侧**（路径都在宿主仓库的 `packages/` 下）：

- 原生 `subagent`（〔源码〕`core/src/tool/plugin/subagent.ts`）：无条件内建登记，
  `codemode: false`——所以它不在代码模式的目录里，是直接工具。入参 `agent` /
  `description` / `prompt` / `model` / `sessionID`。调用立刻返回，子会话作为宿主的
  后台作业运行（〔源码〕`core/src/session/subagent-job.ts`：作业类型 `subagent`，
  `background: true`）。
- 续用（〔源码〕同上）：带 `sessionID` 就续用那个子会话，它必须是当前会话的孩子。
  〔沙箱〕是通的：第二次带着 `sessionID` 调用成功，孩子还是那 1 个，答上了第一轮
  记住的词，没报找不到会话。社区有一条“续用总是报找不到”的开放 issue（#59293），
  在沙箱里没有复现（只跑了一次，没去查它为什么报）。
- 深度（〔源码〕`core/src/session/subagent-depth.ts`，在 `subagent.ts` 第 118–125 行
  调用）：上限是 `experimental.subagent_depth`，默认 1。超了报
  `Subagent depth limit reached (1). Increase "experimental.subagent_depth" to allow nested subagents.`
  按引用关系，全仓库只有两处用这个检查：原生 `subagent` 工具和宿主自动化
  （`core/src/automation.ts`）。〔沙箱〕一个允许调原生 `subagent` 的子会话去调，
  报的就是这句原文，没有建出孙子会话。
- 重启续跑（〔源码〕`core/src/session/subagent-job.ts`）：宿主按作业的恢复记录把子会话
  续跑起来。注释写明：只有调用方明确取消才释放孩子的占用；服务关闭打断了这个作业时，
  孩子要留到下次启动还能续跑。
- 宿主自带的“打断会话”工具（〔源码〕`core/src/tool/plugin/session-interrupt.ts`；只在
  代码模式总开关 `full_codemode` 打开时登记）。做法：取消该会话的后台作业 → 打断 →
  再取消一次 → 按 `parentID` 列出孩子逐个照做；拒绝打断自己或自己的上级。文件里有一句
  注释：“被取消的作业不发完成通知，所以这些会话不会再被叫醒”（第 26–27 行）。它说的
  是**被停的那些会话自己**不会再被作业叫醒——先取消作业再打断，就是为了让它们停下来
  之后保持安静；不是说它们的父会话收不到通知。〔沙箱〕父会话照样收到“已取消”并被
  叫醒（见 Verification ⑤）。这份草案的上一版把这句读成了后者，已更正。
- 插件能调到的接口（〔源码〕）：
  - 插件接口（forge 的 v2 入口用的 promise 层）：会话类有 `session.list`、
    `session.interrupt`、`session.get`、`session.remove`、`session.prompt` 等
    （`plugin/src/promise/session.ts` 第 225–245 行，另有实验性的 `session.wait`）。
    **没有作业类的**：`ctx.shell` 只有一个“命令启动前”的钩子
    （`plugin/src/promise/shell.ts`）；`experimental` 组只有终端读取、生图、工件三样
    （`plugin/src/promise/plugin.ts` 第 36–41 行）；整个插件 SDK 包里也没有任何地方
    引用作业接口。
  - 删子会话：〔源码〕〔沙箱〕直接调宿主的 `DELETE /api/session/<id>` 删一个子会话，
    它名下的宿主后台作业跟着一起没了，父会话收不到任何通知；插件接口里的
    `session.remove` 是不是同一个效果，〔未验〕（forge 代码里的注释引的接口说明是
    “停止执行，并递归删除子会话”，`plugin.ts` 第 10232–10234 行）。
  - 宿主的 HTTP 接口有两组能停掉后台作业：
    - `GET /api/shell?location[directory]=…` 列出某个目录下正在跑的命令，
      `DELETE /api/shell/:id` 终止并移除一条（`protocol/src/groups/shell.ts`）。
      **这组不在实验性分组里。** 智能体用 shell 工具跑的命令都记在这本账上
      （`core/src/shell.ts` 第 140–158 行的服务说明）。〔沙箱〕列出来的每条带着
      `metadata.sessionID`，就是启动它的会话；命令的编号和宿主作业的编号是同一个。
    - `GET /api/experimental/job`（可按 `sessionID` 过滤，`descendants=true` 时连同
      子孙会话的）和 `POST /api/experimental/job/:id/cancel`
      （`protocol/src/groups/job.ts`）。管所有类型的宿主作业（shell、代码模式、生图、
      视频）。**两个都标着“实验性，不保证兼容”**。〔沙箱〕从沙箱驱动里直接调是通的
      （列作业回的作业类型字段叫 `kind`，取消回 204）。
  - **forge 的 v2 入口够得到宿主的 HTTP 接口**：它本来就有一条直连宿主的通道，从
    service.json 读地址和口令（〔源码，forge〕`plugin.ts` 第 10055–10062 行），读消息、
    打断后备、原生孩子遍历三条调用都走在上面（第 10064–10114、10222–10265 行）。
    注释里写着这几条真机验证过；我今天没有重新验。
  - 另一套插件接口（effect）的类型里有作业接口（`ExperimentalApi.job.list/cancel`，
    `client/src/effect/api/api.ts` 第 2630 行），但 forge 的 v2 入口用的是 promise 接口，
    不走这条。运行时通不通：〔未验〕。
- “只打断，够不着正在跑的命令”：TUI 客户端的注释写着，正在跑的 shell 不持有
  drain，`session.interrupt` 够不着它，所以 TUI 是另行中止请求的，服务端那条命令
  照跑（〔源码〕`tui/src/mini/stream-v2.transport.ts` 第 1868–1870 行）。这句话说的
  是 TUI 自己那条被阻塞的请求，不是服务端的打断。〔沙箱〕对正在跑宿主前台长命令的
  子会话，从服务端调打断：回合中止，5 秒后命令进程消失。打断真够不着的是另一种
  情况：子会话**已经收工**、名下还留着宿主的后台作业——这时打断是空操作（回
  `interrupted:false`），命令照跑，见 D4。宿主源码里对这种作业也有一句说明：“孩子
  自己的后台命令，在孩子向父会话报告之后仍然算数：它的通知会把孩子再叫醒一次，
  所以孩子的工作还没完”（〔源码〕`core/src/session/background.ts` 第 26–29 行）。
  〔沙箱〕见到的正是这样。
- 子会话的记录：〔沙箱〕带 `parentID`、`location.directory` 和 `outcome`（见过
  `succeeded`、`interrupted`、`failed` 三种）；标题就是派发时给的 `description`。
- 孩子继承父会话的会话级规则。带 `parentID` 建会话、没有另外给权限时，宿主把父会话的
  会话级权限规则和元数据原样抄给孩子（〔源码〕`core/src/session.ts` 第 315–318 行，
  注释说这是为了让按会话取规则的宿主策略对整个家族一视同仁）；原生 `subagent` 建孩子
  只传父会话、标题、代理、模型四样（`core/src/tool/plugin/subagent.ts` 第 174–180
  行），所以原生孩子一定继承。
- 权限怎么判：代理规则、会话规则、项目里保存的“总是允许”按这个顺序摊平，**最后一条
  匹配的生效**，一条都不匹配时默认问用户；配置里的拒绝排在保存的放行前面
  （〔源码〕`core/src/permission.ts` 第 102–119、212–238 行）。
- “没人应答时自动裁决”只给了定时任务（〔源码〕`core/src/automation.ts` 第 282、813
  行），原生子会话不在其列。所以后台孩子里落到“问用户”的请求，没有人看就一直挂着。
- 打断的语义（〔源码〕`core/src/session/execution.ts` 第 29–42 行）：会话空闲时打断是
  空操作；打断被接受就立刻返回，收尾在后台异步进行；返回值说明是不是真的打断了正在
  跑的那一轮。孩子那一轮以“被打断”收场时，宿主自己会取消登记在这个孩子名下的宿主
  作业（同文件第 169 行）。这和〔沙箱〕见到的对得上：forge 工人手里的 `forge_shell`
  进程不是宿主作业，打断后还在，要插件自己取消。
- 宿主有一个“会话要空闲了”的钩子，回调里带着这个会话和它所有后代还在跑的后台作业
  清单——哪条命令（带命令号）、哪个原生子代理（带子会话号）（〔源码〕
  `plugin/src/promise/session.ts` 第 159–205 行、`core/src/session/background.ts` 第
  26–64 行）。forge 已经登记了这个钩子，但现在只取了会话号，清单没用上
  （〔源码，forge〕`plugin.ts` 第 9801–9805 行）。
- 内建代理（〔源码〕`core/src/plugin/agent.ts` 第 56–94 行）：Build 是主代理，允许提问；
  `general`、`explore` 是子代理，既不许提问也不许再派发。宿主自带的 Plan 模式是切换
  到另一个代理（`core/src/plugin/plan.ts` 第 14–53 行）：不许写，只许写 plan 目录，
  **允许提问**；“别让子代理去改”只是提示词里的一句话。

**forge 这一侧**：

- 工人的工具面（〔源码，forge〕`src/roster-compile.ts` 的 `toolsFaceFor`）：每个
  forge-\* 工人的代理文件里 `task: false`，两个旧的 shell 键也是 false；只读形状再封掉
  写类家族。宿主归一配置时，把 `tools` 里的键名过一遍 `normalizeAction`——`task` 归一成
  `subagent`，`false` 变成 deny（〔源码，宿主〕`core/src/config/normalize.ts` 第 539–550
  行、`core/src/v1/config/migrate.ts` 第 28–34 行）。所以在原生路上，工人照样派不了
  下级，有两道保证：宿主的深度检查（工人总是子会话），和这条归一后的拒绝。forge 自己
  那条“子会话禁再派发”的封印规则，动作名写的是 `task`（老账）——动工时对一遍，不把
  它算作这里的保证。
- 主代理不封派发工具（单测钉着“主代理保留 task”：`tests/dispatch-wiring.test.mjs`）。
- crew 的编排者就是跑 `/crew`、调 `crew_begin` 的那个会话
  （`openspec/specs/crew-harness/spec.md`）。规格里已经有一条“原生子会话在飞时不发
  续跑简报”的门，按 `parentID` 走会话树，本来就认宿主原生的孩子。但规格里也写着
  子任务“以并行的 `task` 调用成波执行”——换路后这句要改。
- 插件的权限带看得到原生 `subagent` 的调用，也能拒绝它（〔沙箱〕拒绝后不建子会话，
  状态页“缺陷 F2”的可行性）。草稿期禁令现在**不拦**原生 `subagent`（〔沙箱〕plan
  在草稿期，父会话调原生 `subagent` 照样建出了子会话；〔源码，forge〕禁令是按写类
  工具名单判的——`plugin.ts` 的 `WRITE_TOOLS`，名单里有 `task`、没有 `subagent`）。
- 工人在原生路上**能提问**。〔沙箱〕原生派出的 forge 工人调了宿主的 `question` 工具，
  没人答就一直挂着（一次 40 秒后被探针打断，一次挂了 3 分多钟）。task 引擎派后台
  孩子时会在孩子会话上盖一道“禁止提问”（〔源码，forge〕`src/dispatch-async.ts` 的
  `QUESTION_DENY_*`）；原生派发的孩子是宿主建的，这道印没人盖。工人代理文件的
  `tools` 里也没写 `question`（`toolsFaceFor` 只写 `task` 和两个旧 shell 键；真机和
  沙箱里编译出来的文件都是这三行）。〔沙箱〕宿主给 forge 工人归一出来的权限里，
  确实没有 `question` 这一条。宿主对自己的内建子代理是封了的：`general` 的权限里
  就有 `question: deny`（〔源码，宿主〕`core/src/plugin/agent.ts` 第 68–71 行；
  〔沙箱〕宿主列出来的 `general` 权限里也有这一条）。
- 工人代理文件的描述和正文里写着“用 `task` 工具派发”（〔真机〕〔沙箱〕
  `src/roster-compile.ts` 编译出来的文件都是）。换路以后这句就不对了，要跟着改。
- task 引擎建孩子时一共设了七样（〔源码，forge〕`src/dispatch-async.ts` 的
  `createChildSession`）：父会话、标题、代理、钉住的模型、孩子所在的目录（按会话
  锚点解析）、v1 写法的提问封印、v2 写法的提问封印加“不许再派发”。换到原生路，
  前四样宿主自己会做（〔沙箱〕标题用的是派发时给的 `description`；代理文件里钉了
  模型的，孩子记录里就是那个模型）；目录见下一条；“不许再派发”由宿主的深度检查
  和归一后的拒绝各守一道；提问封印没人盖，见 D6。
- 原生派出的子会话落在**父会话的目录**里。〔沙箱〕三次取样：父会话在两个新建的
  临时目录里时，原生派出的 `general` 子会话，记录里的目录和父会话一字不差（两次），
  孩子用宿主 shell 不带目录参数跑出来的路径也是它；父会话在主沙箱目录里时，原生
  派出的 forge 工人，记录里的目录也是父会话的（一次），工人在里面调 `forge_shell`
  不带目录参数，作业的 `cwd` 就是它。在那之前最后一次让宿主初始化的目录，是一个
  已经删掉的临时目录，没有被当成孩子的目录用。工人这一条只在主沙箱目录里测过；
  在新目录里测工人的那一步，两次都没测成（原因记在状态页）。
- 原生派出的子会话，记录里带着一条会话级权限 `forge_shell: allow`（〔沙箱〕三次取样
  都有），父会话刚建出来时没有。已经查清，不是异常：forge 的 `context` 钩子在 forge
  主会话第一次构建上下文时，把这条“会话补救规则”（`SESSION_RESCUE_RULE`，属于
  `worker-shell-session-allow` 那个 change）种到主会话上（〔源码，forge〕`plugin.ts`
  第 9586–9592 行，注释里叫“继承通道”）；之后建的孩子按上面那条继承它，不管孩子
  用的是哪个代理。父会话“刚建出来时没有”，是因为那时还没发过第一句话。上一版写的
  是“是谁写进去的，没查”，已更正。
- 真机的 forge 会话原生派发整条链路是通的（〔真机〕）；沙箱里能用它派出 forge 工人
  （〔沙箱〕）。

十条路子分两类：前五个（slim、Omacode、nexus、ahetzm、agnusdei）是“原生，或者贴着
原生”，和 D 同路；后五个自己建会话、自己管生命周期。**没有一家去终止孩子留在宿主
那边的命令**：十家的源码里都搜不到对宿主 shell / 作业取消接口的调用（按关键字搜的，
不是逐行读），它们杀的只是自己启动的进程。另有三家会在自己建的会话上用
`session.remove` 把会话删掉（smart-subagents、mission-control、dynamic-workflows 的
界面端），那是删会话，不是终止命令。搜到的唯一一处是 kimaki——一个 Discord
客户端，不是插件——它的 `/abort` 在打断之后会终止用户自己敲的 shell
（〔源码〕`src/prompt.ts` 第 216–231、276–288 行）。

## Goals / Non-Goals

**Goals**

- v2 上只有一个派发面：宿主原生的 `subagent`。
- `/forge stop` 能停掉本会话的原生子代理，连它们留在宿主那边的后台命令一起。
- forge-\* 工人的预设、三个 harness 的安全互锁，换路之后行为不变。
- 出问题能切回去。

**Non-Goals**

- 不重做任何宿主已经做了的事（执行、通知、续跑、读子会话、续发消息）。
- 不给原生派发加“谁能派谁”的门。

## 对照同行之后改了什么（2026-11-25）

一句话：六件里五件没动，都有同行的先例，或者同行没有对应物；**D4 改了**。另有三处是
我上一版写错或读错的，已更正。

| | 上一版 | 现在 | 依据 |
| --- | --- | --- | --- |

1. D4 上一版说“在插件里直接向宿主的接口发请求要自己拿端口和口令，不推荐”。不对：
   forge 的 v2 入口本来就有这条通道，三条调用在用（见 Context）。是我没查自己家的
   代码。
2. 原生孩子的记录里那条 `forge_shell: allow`，上一版写“是谁写进去的，没查”。查清了，
   见 Context。
3. 上一轮探针 ④ 里有一条“只打断之后，父会话收到了一条‘仍在运行’”，我把它记成了
   打断的效果。它其实是孩子第一次收工时自己发的汇报，正文就是孩子第一轮的回答。
   补测的三臂和这个对得上：两条臂里它落在动作前 2 秒的窗口内，另一条臂里它落在
   窗口外、没被计入（见 Verification ⑧）。

没采纳的做法（都读过，理由各写一句）：

- **v2 上不留自管引擎**（slim）：forge 的 `task` 引擎多带几样原生没有的东西，留一版
  退路（见 D1）。
- **保留自己的编排层，底下程序化去调内建 `subagent`**（nexus，〔源码〕
  `src/orchestrator.ts` 第 3563–3614 行）：能留着自己的队列、依赖图、重试，孩子又挂得
  上 `parentID`。你已经明确不要同步派发和排队，所以不走这条，记下来备查。
- **插件级钩子，把后台孩子里的任何提问、或任何“问用户”的请求一律改判为拒绝**
  （opencode-workflows；ahetzm 追加“不许再派人”用的是同一招，〔源码〕`src/index.ts`
  第 261–267 行）：会盖过用户在代理配置里的显式选择（见 D6）。
- **提问超时兜底**（slim；mission-control 的权限 2 分钟超时）：先不做（见 D6）。
- **`/abort` 连收件箱里排队的消息一起清**（kimaki）：那是用户排给主会话的消息，
  forge 的 `/forge stop` 现在也不动它（见 D4）。

## Decisions

下面六件需要用户拍板。草案里我先各选了一个默认项，并写了理由。

### D1 开关的默认值与保留期（默认：v2 上默认走原生，开关保留一版）

配置项拟为 `agent.forge.dispatchEngine`，取值 `native`（v2 上的默认）或 `task`。
v1 宿主没有这个开关，永远走原来的 `task` 引擎。保留一个版本周期的实机观察，
之后再议删除——换派发面是这次迁移里最大的一步，退路不能一次拆光。

同行的对照：slim 在 v2 上不留自管引擎——旧的自管模式 `managed` 明确不支持，会被当成
`native` 并给一个警告（〔文档〕`README.md` 第 233–236 行）。我这里比它保守一步：
forge 的 `task` 引擎比 slim 的自管模式多带几样原生没有的东西（同步派发、并发上限加
排队、按次下发的权限、报告文件、重启后的收养），万一原生路在你真机上出问题，切回去
是立刻能用的。开关不露给模型（见 D2），不妨碍“v2 上只有原生这一个派发面”。

### D2 插件的 `task` 在 v2 上怎么处置（默认：不再登记给模型）

代码留着：开关切到 `task` 时才登记。默认配置下，模型在 v2 上看不到插件的 `task`，
只看得到宿主原生的 `subagent`。这样“一个派发面”是事实，不是靠提示词劝出来的。

同行的对照：ahetzm 的 orchestrator 同一个包两个入口，v2 入口完全不自己派发，只用宿主
的 `agent.transform` 定义代理（〔源码〕`src/index.ts`）；slim 在 v2 的原生模式下只留
查询、取消、代答权限、进度上报四个薄控件，不登记派发工具（〔文档〕
`docs/background-orchestration.md` 第 8–28 行）。

### D3 派发日志和报告文件（默认：留一份最小的子代理记录，报告文件不再生成）

原生路上，执行不经过插件，插件原有的派发日志行、报告文件、进度通知都不会再
产生。但有两处还要用到“本会话有哪些子代理、结果如何”：crew 的续跑门和摘要，
以及 `/forge stop`。默认做法是插件只**旁观**：监听宿主的会话事件，记下本会话的
原生子会话和它们的终态，不从执行路径里产生任何记录。报告文件不再生成——子会话
的最终报告由宿主放在完成通知里。〔沙箱〕要记的东西宿主的会话记录里都有
（`parentID`、`outcome`，见 Context），所以这份记录可以直接从宿主的会话列表读。

从哪儿读：2.4.0 的插件接口里有 `session.list`（见 Context）。forge 写那段适配代码时
（2.3.2）这层还没有它，所以列孩子一直走的是直连宿主的那条通道；动工时改成优先用
接口，真机上没有就退回通道。“谁还在飞”另有一个来源：宿主的空闲钩子会直接给出这个
会话和它所有后代还在跑的作业清单（见 Context）。同行的对照：slim 的 `task_cancel`
每次用一次查询核对 `parentID`，不记账、不租约（〔源码〕
`src/tools/native-task-control.ts` 第 483–528 行）；agnusdei 的 orchestrator 只从“会话
已建立”事件学一张父→子的内存表，忙闲向宿主查（〔源码〕
`src/core/session/child-sessions.ts`）。

### D4 `/forge stop` 怎么停（默认：连孩子留在宿主那边的后台命令一起终止，子会话保留）

原设想是照宿主自带工具的配方：取消该会话的后台作业 → 打断 → 再取消 → 孩子逐个。
插件接口里没有“列出/取消后台作业”，这个配方不能照搬；但 forge 直连宿主接口的那条
通道够得到（见 Context）。

〔沙箱〕今天的 `/forge stop` 对原生派出的子代理是完全看不见的：对两个正在忙的
原生子代理调它，回的是 “No async dispatches in flight for this session … nothing
to stop.”，两个孩子照样忙。所以换路后它必须重做。

**上一版的结论已改。** 上一版写的是“有一小块停不干净，默认接受”：已经收工的子会话
名下还留着宿主的后台命令时，打断是空操作，理由是插件“够不着”宿主的作业。对照同行、
重读源码之后，这个理由不成立：forge 本来就有一条直连宿主接口的通道，宿主那头还有
一组**不属于实验性**的接口专门管这个。

〔沙箱〕补测（探针 ⑧）：三个 `general` 孩子各自留了一条 150 秒的宿主后台命令，都已
经收工，各用一种做法——

| 做法 | 命令 | 孩子 | 父会话收到 |
| --- | --- | --- | --- |
| 只终止命令（`DELETE /api/shell/:id`，204） | 3 秒后进程消失 | 被叫醒，又答了一轮；记为 `succeeded` | **“已完成”**，正文是“命令以 `Shell.NotFoundError` 结束，没有输出预期的结果” |
| 终止命令，36 毫秒后打断（回“确实打断了”） | 3 秒后进程消失 | 没来得及答；记为 `interrupted`；之后 75 秒内没再被叫醒 | **“已取消”** |
| 只用实验性的作业取消（204） | 3 秒后进程消失 | 被叫醒，又答了一轮；记为 `succeeded` | **“已完成”**，正文是“命令在跑完之前被取消了” |

三个结论：两种接口都终止得了命令；**只终止命令不够**——孩子会被这一下叫醒，答一轮，
父会话收到的状态是“已完成”；**终止之后紧接着打断**，才是干净的“停”。

三种孩子各试过（〔沙箱〕，第一轮）：回合还在跑的，前台命令随打断一起停；forge 工人
手里的 `forge_shell` 进程不是宿主作业，打断后还在，要插件自己取消；已收工、留着宿主
后台命令的，就是上面这张表。所以配方里“终止宿主那边的命令”和“取消插件自己的作业”
是两步。

所以 `/forge stop` 在原生路上这样做：

1. 按 `parentID` 走会话树，找出本会话的子会话、孙会话。
2. **先终止**这些会话留在宿主那边的后台命令：列出该目录下正在跑的命令，只留
   `metadata.sessionID` 属于这一家子的，逐条终止。别的会话的命令、你自己在界面上敲
   的命令不碰。
3. **紧接着打断**每个子会话（`session.interrupt`，插件接口）。
4. **回访**，最多三轮、前后几秒钟：有孩子又被叫醒就再打断一次；中途新冒出来的孩子
   也算进来。
5. **最后**取消这些会话名下插件自己的 forge 作业（插件自己的作业表，现有能力）。

“先打断、后取消 forge 作业”这一条不变：顺序反过来，工人会“报假完成”（见 Risks）。

回执逐个孩子说清楚：打断了几个、本来就没在跑的几个、终止了几条命令、哪一步没做成。
你说的“排队的也取消”，在原生路上没有对应物——原生派发不排队。宿主收件箱里排着等
下一轮的消息是你排给主会话的，`/forge stop` 默认不动它。

仍然要你知道的：

- 代码模式、生图、视频这类宿主作业，只能走实验性那组接口。默认也调；接口不在
  （将来的宿主改了）就跳过，并在回执里说明。〔沙箱〕只测过 shell 这一种。
- 通道用不了时（读不到 service.json，或接口报错），退回“只打断”，回执里写明有几条
  命令没能终止。这时就是上一版写的那个残缺口：命令跑到自己结束，孩子被叫醒再答
  一轮，父会话再收到一条“已完成”。
- 把子会话**整个删掉**（`session.remove`）依然不默认用：命令跟着没了，但子会话的
  记录也没了，事后查不到它做过什么。要不要做成可选项，由你定，默认不做。
- 不走的两条绕路：把 forge 的 v2 入口改走 effect 接口（那套接口的类型里有作业接口，
  但这是一次大得多的迁移，不该为这一件事做）；在插件里自己杀进程。

需要你拍板的：

- 同意 `/forge stop` 为此走宿主的 HTTP 接口吗？这是插件接口目前没有的能力，同行里
  没有先例（见“同行这一侧”）。我的建议是走：终止命令那组接口不是实验性的，通道是
  forge 已经在用的。
- 要不要给宿主提一个请求，请他们在 promise 适配层也暴露作业接口——对外发声是你的
  授权域。

### D5 草稿期禁止派发（默认：保留，让权限带也拦原生 `subagent` 的调用）

plan 在草稿期禁止写，也禁止派发——否则派出去的工人替它把写了。换到原生路，
派发不再经过插件的 `task`，这条禁令只剩权限带这一道可以执行。默认做法：让权限带
对原生 `subagent` 的调用执行同一条禁令，拒绝文案不变。它现在**不拦**：〔沙箱〕plan
在草稿期，父会话调原生 `subagent` 照样建出了子会话；〔源码，forge〕禁令是按写类
工具名单判的，名单里有 `task`、没有 `subagent`。所以这一项不是“保留”，是要新加
一条判定。（对照的那一步没拿到结果：同一个父会话被要求调插件的 `task`，它 45 秒
内没调，原因没记录。草稿期拒 `task` 是现行的行为，由原来的草稿门测试管，不在这里
重证。）

这和已经撤掉的 change #2 不是一回事：change #2 要给原生派发加的是派发门（分区、
形状、池归属、crew 待定与合规）；D5 拦的是“plan 草稿还没批准时不能派人去干活”，
是 plan 自己的安全互锁。如果你认为草稿期也该允许原生派发，这项改成不拦，实现上
更简单。

同行里没有等价的东西：宿主自带的 Plan 模式允许提问，靠切换代理来限写；Omacode 的
“plan”是一个去独立工作树里做调研的角色（〔源码〕`packages/state/src/roles.ts` 第
235 行）。两家都不是“草稿没批准前不许派人”。所以这一项没有先例可参照，按 forge
自己的 plan 约定走。

### D6 工人在原生路上不能提问（默认：把封印写进工人代理文件）

来龙去脉见 Context。默认做法：插件编译工人代理文件时，把 `question: false` 一并
写进 `tools`（`src/roster-compile.ts` 的 `toolsFaceFor`，加一行）。宿主归一配置时
会把 `tools` 里的 `false` 变成对应动作的拒绝（〔源码，宿主〕
`core/src/config/normalize.ts` 第 539–550 行），和宿主给内建 `general` 盖的印是同
一种。〔沙箱〕一个 `tools` 里写了 `question: false` 的代理，原生派出后答的是“没有
提问工具”，没调任何工具（只跑了一次）。

只在 v2 上加，所以同一份配方在 v1 和 v2 上编译出来的工人文件会差这一行。v1 入口
原样不动——v1 的同步派发允许孩子提问（你当时在场），这是现行约定，不在这次改。

同行的先例（理由和这里是同一个：孩子在后台，没人回答）：

- 宿主自己的内建子代理 `general`、`explore` 就拒提问（〔源码〕`core/src/plugin/agent.ts`）。
- slim：孩子默认不向人提问，注释原话 “Subagents don't ask the human by default: a
  parked child question has no headless answerer. Explicit config wins.”
  （〔源码〕`src/agents/index.ts` 第 739–743 行）。
- Omacode：每个角色都追加一条拒提问，注释原话 “Nobody sits at a background worker,
  so a question it puts up is never answered and the worker hangs on it”，并记着实跑里
  有工人提了四次；拿不准的事改成去问“助手”子代理（〔源码〕
  `packages/state/src/roles.ts` 第 131–133 行、`packages/micromanager/src/helpers.ts`）。
- opencode-workflows：用钩子把后台孩子里的任何提问改判为“拒绝 + 一句解释”
  （〔源码〕`src/opencode/permissions.ts` 第 84–119 行）。

ahetzm 的 orchestrator 没封，是个缺口。

不选的三条：

- **插件级钩子**，让权限带对所有带 `parentID` 的会话拒绝 `question`，或者把后台孩子里
  的任何提问、任何“问用户”的请求一律改判为拒绝（opencode-workflows）。好处是连不是
  forge 的自定义代理也盖到；代价是会盖过用户在代理配置里的显式选择，而且权限带在孩子
  会话里是不是每条工具调用都过一遍，〔未验〕。forge 工人有代理文件这道印就够，别的
  代理是你自己的配置。
- **提问超时兜底**：slim 监听提问表单，超时自动答“没人回答，自己决定并继续”
  （〔源码〕`src/hooks/question-timeout/core.ts`，默认开不开我没查）；mission-control
  把权限请求转给用户，2 分钟没人答就拒绝并附解释（〔源码〕
  `src/lib/job-permissions.ts` 第 15–19 行）。先不做；真机上要是出现“盖了印还挂着”，
  再加。
- **让孩子问父会话、不问人**（smart-subagents 的 `ask_parent`、slim 的 `task_report`）：
  这是宿主原生的能力，你说过不自己封装。

也不走会话规则：在主会话上种一条会话级的“拒提问”确实会被所有孩子继承（见
Context），但主会话自己也就不能提问了。残留的一种情况：主会话上要是有人种了会话级
的“允许提问”，孩子会继承它，并且因为它排在代理规则后面而盖过这道印；forge 自己
不种这一条。

### 定下来的做法（不需要拍板，列出来防止以后搞错）

- 派发：模型直接调原生 `subagent`；forge-\* 工人就是宿主眼里的普通代理预设。
- 工人不能再派下级：宿主的深度检查和归一后的 `subagent` 拒绝各守一道（见 Context，
  〔沙箱〕已实测）。
- 工人代理文件的描述和正文改成新写法：不再写“用 `task` 工具派发”。
- 完成通知、重启续跑、读子会话、续发消息：全部用宿主的。
- 每次派发完成只叫醒父会话一轮（插件不再补发）——代价见 Risks 第一条。
- `/forge stop` 的配方见 D4：终止命令 → 打断 → 回访 → 取消 forge 作业。

## Risks / Trade-offs

- **插件补发的唤醒没有了，包括宿主给不了的那部分。** 插件现在除了重复的那条，还会
  在宿主给不了结果的场合（中止原因、结果流丢失）补发唤醒。原生路上派发不经过
  插件，这些唤醒都不会再有。宿主自己通不通知：〔沙箱〕取消和异常结束两种都通知
  了，也都叫醒了父会话（见 Verification ⑤）。没测的：真实的上游超时或限流造成的
  异常结束（沙箱里是用“模型不存在”造的）；同时打断多个孩子时父会话被叫醒几轮。
- **看守不再覆盖原生子会话。** 插件的“结果流丢失”这类判定随之消失（少一种误判的
  来源）；但按同样的道理，子会话失联时也不再由插件兜底（推断）。crew 有规格里
  “原生子会话在飞”那道门兜着；非 crew 的派发靠宿主。
- **`/forge stop` 多依赖一样东西：forge 直连宿主接口的那条通道**（D4）。终止孩子留下
  的命令只能走它，插件接口里没有。通道在，停得干净；通道不在，退回“只打断”，回执
  里会写明。宿主以后要是把作业接口也暴露给 promise 适配层，这条依赖就能去掉。
- **只终止命令、不接着打断，会报“已完成”。** 终止这一下会把孩子叫醒，孩子答一轮，
  父会话收到的状态是“已完成”（〔沙箱〕，见 D4 的表）。所以终止和打断必须连着做，
  之后还要回访。
- **顺序错了会“报假完成”。** 先取消工人的 forge 作业、后打断，工人会被自己那次
  轮询叫回来，接着把回合跑完、照常交报告，父会话收到的是“已完成”（〔沙箱〕试出来
  的）。所以 `/forge stop` 必须先打断、后取消作业。
- **通道不在时，带宿主后台命令的孩子会“复活”。** 只打断一个已收工、名下还有宿主
  后台命令的孩子是空操作；命令跑完，孩子被叫醒再答一轮，父会话再收到一条“已完成”
  （〔沙箱〕）。D4 的配方做全了就不会；退回“只打断”时就是这样。
- **工人会卡在提问上**（D6）：不盖印的话，原生派出的工人一提问就没人答。
- **没有同步派发了。** 原生只有后台。你已经明确不要同步派发。
- **没有并发上限和排队。** 一次派出多少个由模型和你决定，插件不再限。
- **crew 编排者必须是主会话**（深度上限 1）。这和现状一致（工人本来就当不了
  编排者）；以后要嵌套，调宿主的 `experimental.subagent_depth`。
- **v2 的行为和 v1 分叉。** v1 入口原样不动，所以同一个插件在两类宿主上的派发
  行为不同。README 要写清楚。
