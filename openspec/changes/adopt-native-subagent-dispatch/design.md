# Design: adopt-native-subagent-dispatch

> **草案，等用户过目（本地 2026-11-25 起草，同日按沙箱实测改过一轮）。没批准不开工。**
> 每条事实后面标了它是怎么知道的：
> 〔源码〕读过宿主 v2.4.0 标签（提交 `44aed4f`）或 forge 自己的源码，没有实跑；
> 〔真机〕在真机上实际调用过；〔沙箱〕在沙箱里实际跑过；
> 〔未验〕只有推断，或连源码都没查到。
> 沙箱事实的口径统一写在 Verification 一节的开头。

## Context

**宿主这一侧**（路径都在宿主仓库的 `packages/` 下）：

- 原生 `subagent`（〔源码〕`core/src/tool/plugin/subagent.ts`）：无条件内建登记，
  `codemode: false`——所以它不在代码模式的目录里，是直接工具。入参 `agent` /
  `description` / `prompt` / `model` / `sessionID`。调用立刻返回，子会话作为宿主的
  后台作业运行（〔源码〕`core/src/session/subagent-job.ts`：作业类型 `subagent`，
  `background: true`）。
- 续用（〔源码〕同上）：带 `sessionID` 就续用那个子会话，它必须是当前会话的孩子。
  〔沙箱〕是通的：第二次带着 `sessionID` 调用成功，孩子还是那 1 个，答上了第一轮
  记住的词，没报找不到会话。社区有一条“续用总是报找不到”的开放 issue（#59293），
  在沙箱里没有复现（只跑了一次，没去查它为什么报）。
- 深度（〔源码〕`core/src/session/subagent-depth.ts`，在 `subagent.ts` 第 118–125 行
  调用）：上限是 `experimental.subagent_depth`，默认 1。超了报
  `Subagent depth limit reached (1). Increase "experimental.subagent_depth" to allow nested subagents.`
  按引用关系，全仓库只有两处用这个检查：原生 `subagent` 工具和宿主自动化
  （`core/src/automation.ts`）。〔沙箱〕一个允许调原生 `subagent` 的子会话去调，
  报的就是这句原文，没有建出孙子会话。
- 重启续跑（〔源码〕`core/src/session/subagent-job.ts`）：宿主按作业的恢复记录把子会话
  续跑起来。注释写明：只有调用方明确取消才释放孩子的占用；服务关闭打断了这个作业时，
  孩子要留到下次启动还能续跑。
- 宿主自带的“打断会话”工具（〔源码〕`core/src/tool/plugin/session-interrupt.ts`；只在
  代码模式总开关 `full_codemode` 打开时登记）。做法：取消该会话的后台作业 → 打断 →
  再取消一次 → 按 `parentID` 列出孩子逐个照做；拒绝打断自己或自己的上级。文件里有一句
  注释：“被取消的作业不发完成通知，所以这些会话不会再被叫醒”（第 26–27 行）。它说的
  是**被停的那些会话自己**不会再被作业叫醒——先取消作业再打断，就是为了让它们停下来
  之后保持安静；不是说它们的父会话收不到通知。〔沙箱〕父会话照样收到“已取消”并被
  叫醒（见 Verification ⑤）。这份草案的上一版把这句读成了后者，已更正。
- 插件能调到的接口（〔源码〕）：
  - `session.interrupt`：正式接口，插件的适配层里有它
    （`plugin/src/promise/adapter.ts`）。
  - 列出后台作业 `GET /api/experimental/job`（可按 `sessionID` 过滤；
    `descendants=true` 时连同子孙会话的）和取消作业
    `POST /api/experimental/job/:id/cancel`（`protocol/src/groups/job.ts`）。
    **两个都标着“实验性，不保证兼容”**。〔沙箱〕从沙箱驱动里直接调是通的
    （列作业回的作业类型字段叫 `kind`，取消回 204）。
  - **forge 的 v2 入口调不到这两个实验接口**：它用的是插件的 promise 接口，这层适配
    （`plugin/src/promise/adapter.ts`）是挑过的——`experimental` 组只有终端读取、生图、
    工件三样，没有作业；整个插件 SDK 包里也没有任何地方引用作业接口。这层暴露的
    会话类接口有 `session.list`、`session.interrupt`、`session.get`、`session.remove`、
    `session.prompt` 等。〔源码〕〔沙箱〕直接调宿主的 `DELETE /api/session/<id>` 删一个
    子会话，它名下的宿主后台作业跟着一起没了，父会话收不到任何通知；插件接口里的
    `session.remove` 是不是同一个效果，〔未验〕。
  - 另一套插件接口（effect）的类型里有作业接口（`ExperimentalApi.job.list/cancel`，
    `client/src/effect/api/api.ts` 第 2630 行），但 forge 的 v2 入口用的是 promise 接口，
    不走这条。运行时通不通：〔未验〕。
- “只打断，够不着正在跑的命令”：TUI 客户端的注释写着，正在跑的 shell 不持有
  drain，`session.interrupt` 够不着它，所以 TUI 是另行中止请求的，服务端那条命令
  照跑（〔源码〕`tui/src/mini/stream-v2.transport.ts` 第 1868–1870 行）。这句话说的
  是 TUI 自己那条被阻塞的请求，不是服务端的打断。〔沙箱〕对正在跑宿主前台长命令的
  子会话，从服务端调打断：回合中止，5 秒后命令进程消失。打断真够不着的是另一种
  情况：子会话**已经收工**、名下还留着宿主的后台作业——这时打断是空操作（回
  `interrupted:false`），命令照跑，见 D4。宿主源码里对这种作业也有一句说明：“孩子
  自己的后台命令，在孩子向父会话报告之后仍然算数：它的通知会把孩子再叫醒一次，
  所以孩子的工作还没完”（〔源码〕`core/src/session/background.ts` 第 26–29 行）。
  〔沙箱〕见到的正是这样。
- 子会话的记录：〔沙箱〕带 `parentID`、`location.directory` 和 `outcome`（见过
  `succeeded`、`interrupted`、`failed` 三种）；标题就是派发时给的 `description`。

**forge 这一侧**：

- 工人的工具面（〔源码，forge〕`src/roster-compile.ts` 的 `toolsFaceFor`）：每个
  forge-\* 工人的代理文件里 `task: false`，两个旧的 shell 键也是 false；只读形状再封掉
  写类家族。宿主归一配置时，把 `tools` 里的键名过一遍 `normalizeAction`——`task` 归一成
  `subagent`，`false` 变成 deny（〔源码，宿主〕`core/src/config/normalize.ts` 第 539–550
  行、`core/src/v1/config/migrate.ts` 第 28–34 行）。所以在原生路上，工人照样派不了
  下级，有两道保证：宿主的深度检查（工人总是子会话），和这条归一后的拒绝。forge 自己
  那条“子会话禁再派发”的封印规则，动作名写的是 `task`（老账）——动工时对一遍，不把
  它算作这里的保证。
- 主代理不封派发工具（单测钉着“主代理保留 task”：`tests/dispatch-wiring.test.mjs`）。
- crew 的编排者就是跑 `/crew`、调 `crew_begin` 的那个会话
  （`openspec/specs/crew-harness/spec.md`）。规格里已经有一条“原生子会话在飞时不发
  续跑简报”的门，按 `parentID` 走会话树，本来就认宿主原生的孩子。但规格里也写着
  子任务“以并行的 `task` 调用成波执行”——换路后这句要改。
- 插件的权限带看得到原生 `subagent` 的调用，也能拒绝它（〔沙箱〕拒绝后不建子会话，
  状态页“缺陷 F2”的可行性）。草稿期禁令现在**不拦**原生 `subagent`（〔沙箱〕plan
  在草稿期，父会话调原生 `subagent` 照样建出了子会话；〔源码，forge〕禁令是按写类
  工具名单判的——`plugin.ts` 的 `WRITE_TOOLS`，名单里有 `task`、没有 `subagent`）。
- 工人在原生路上**能提问**。〔沙箱〕原生派出的 forge 工人调了宿主的 `question` 工具，
  没人答就一直挂着（一次 40 秒后被探针打断，一次挂了 3 分多钟）。task 引擎派后台
  孩子时会在孩子会话上盖一道“禁止提问”（〔源码，forge〕`src/dispatch-async.ts` 的
  `QUESTION_DENY_*`）；原生派发的孩子是宿主建的，这道印没人盖。工人代理文件的
  `tools` 里也没写 `question`（`toolsFaceFor` 只写 `task` 和两个旧 shell 键；真机和
  沙箱里编译出来的文件都是这三行）。〔沙箱〕宿主给 forge 工人归一出来的权限里，
  确实没有 `question` 这一条。宿主对自己的内建子代理是封了的：`general` 的权限里
  就有 `question: deny`（〔源码，宿主〕`core/src/plugin/agent.ts` 第 68–71 行；
  〔沙箱〕宿主列出来的 `general` 权限里也有这一条）。
- 工人代理文件的描述和正文里写着“用 `task` 工具派发”（〔真机〕〔沙箱〕
  `src/roster-compile.ts` 编译出来的文件都是）。换路以后这句就不对了，要跟着改。
- task 引擎建孩子时一共设了七样（〔源码，forge〕`src/dispatch-async.ts` 的
  `createChildSession`）：父会话、标题、代理、钉住的模型、孩子所在的目录（按会话
  锚点解析）、v1 写法的提问封印、v2 写法的提问封印加“不许再派发”。换到原生路，
  前四样宿主自己会做（〔沙箱〕标题用的是派发时给的 `description`；代理文件里钉了
  模型的，孩子记录里就是那个模型）；目录见下一条；“不许再派发”由宿主的深度检查
  和归一后的拒绝各守一道；提问封印没人盖，见 D6。
- 原生派出的子会话落在**父会话的目录**里。〔沙箱〕三次取样：父会话在两个新建的
  临时目录里时，原生派出的 `general` 子会话，记录里的目录和父会话一字不差（两次），
  孩子用宿主 shell 不带目录参数跑出来的路径也是它；父会话在主沙箱目录里时，原生
  派出的 forge 工人，记录里的目录也是父会话的（一次），工人在里面调 `forge_shell`
  不带目录参数，作业的 `cwd` 就是它。在那之前最后一次让宿主初始化的目录，是一个
  已经删掉的临时目录，没有被当成孩子的目录用。工人这一条只在主沙箱目录里测过；
  在新目录里测工人的那一步，两次都没测成（原因记在状态页）。
- 〔沙箱〕还看到一件没查清的事：原生派出的子会话，记录里带着一条会话级权限
  `forge_shell: allow`（三次取样都有），父会话刚建出来时没有。插件里有一条同款的
  “会话补救规则”（〔源码，forge〕`plugin.ts` 的 `SESSION_RESCUE_RULE`，属于
  `worker-shell-session-allow` 那个 change），但按它的注释只对 forge 会话生效，
  而 `general` 子会话的记录里也有。是谁写进去的，没查。
- 真机的 forge 会话原生派发整条链路是通的（〔真机〕）；沙箱里能用它派出 forge 工人
  （〔沙箱〕）。

## Goals / Non-Goals

**Goals**

- v2 上只有一个派发面：宿主原生的 `subagent`。
- `/forge stop` 能停掉本会话的原生子代理。
- forge-\* 工人的预设、三个 harness 的安全互锁，换路之后行为不变。
- 出问题能切回去。

**Non-Goals**

- 不重做任何宿主已经做了的事（执行、通知、续跑、读子会话、续发消息）。
- 不给原生派发加“谁能派谁”的门。

## Decisions

下面六件需要用户拍板。草案里我先各选了一个默认项，并写了理由。

### D1 开关的默认值与保留期（默认：v2 上默认走原生，开关保留一版）

配置项拟为 `agent.forge.dispatchEngine`，取值 `native`（v2 上的默认）或 `task`。
v1 宿主没有这个开关，永远走原来的 `task` 引擎。保留一个版本周期的实机观察，
之后再议删除——换派发面是这次迁移里最大的一步，退路不能一次拆光。

### D2 插件的 `task` 在 v2 上怎么处置（默认：不再登记给模型）

代码留着：开关切到 `task` 时才登记。默认配置下，模型在 v2 上看不到插件的 `task`，
只看得到宿主原生的 `subagent`。这样“一个派发面”是事实，不是靠提示词劝出来的。

### D3 派发日志和报告文件（默认：留一份最小的子代理记录，报告文件不再生成）

原生路上，执行不经过插件，插件原有的派发日志行、报告文件、进度通知都不会再
产生。但有两处还要用到“本会话有哪些子代理、结果如何”：crew 的续跑门和摘要，
以及 `/forge stop`。默认做法是插件只**旁观**：监听宿主的会话事件，记下本会话的
原生子会话和它们的终态，不从执行路径里产生任何记录。报告文件不再生成——子会话
的最终报告由宿主放在完成通知里。〔沙箱〕要记的东西宿主的会话记录里都有
（`parentID`、`outcome`，见 Context），所以这份记录可以直接从宿主的会话列表读。

### D4 `/forge stop` 有一小块停不干净（默认：接受，如实写明）

原设想是照宿主自带工具的配方：取消该会话的后台作业 → 打断 → 再取消 → 孩子逐个。
对着源码查完，这个配方插件照搬不了：forge 的 v2 入口用的是插件的 promise 接口，
这层适配**没有暴露**“列出/取消后台作业”（见 Context）。它调得到的是 `session.list`、
`session.interrupt` 这些。

〔沙箱〕今天的 `/forge stop` 对原生派出的子代理是完全看不见的：对两个正在忙的
原生子代理调它，回的是 “No async dispatches in flight for this session … nothing
to stop.”，两个孩子照样忙。所以换路后它必须重做。

所以在 2.4.0 上，`/forge stop` 能做的是：

1. 按 `parentID` 走会话树，找出本会话的子会话、孙会话；
2. **先**对每个子会话调 `session.interrupt`，打断它手上那一轮；
3. **再**取消这些会话名下插件自己的 forge 作业（插件自己的作业表，现有能力）。

第 2 步必须排在第 3 步前面，这是沙箱里试出来的：顺序反过来，工人会“报假完成”
（见 Risks）。这份草案的上一版写的是先取消作业、后打断，已改。

停不干净的是这样一块：**已经收工的非 forge 子会话，名下还留着宿主自己的后台作业**
（例如 `general` 子会话跑了一条转成宿主后台作业的长命令：它的回合结束了，命令还在
跑）。这时打断是空操作，插件又够不着宿主的作业，命令会跑到自己结束；跑完以后孩子
还会被宿主叫醒再答一轮，父会话再收到一条“已完成”。〔沙箱〕三种孩子各试过：回合
还在跑的，前台命令随打断一起停；forge 工人手里的 `forge_shell` 作业，打断后进程
还在，第 3 步取消后才消失；已收工、带宿主后台作业的，就是上面这一块。

能把这一块也堵上的办法有一个：把子会话**整个删掉**。〔沙箱〕直接调宿主的
`DELETE /api/session/<id>`，子会话名下的宿主后台作业跟着一起没了，父会话收不到
任何通知。代价是子会话的记录也没了，事后查不到它做过什么。默认**不用**这个办法。

需要你拍板的是接不接受这一小块残缺口。默认接受，并把残缺口写进 `/forge stop` 的
返回文案和 README。要不要把“连子会话一起删”做成一个可选项，由你定，默认不做。

不推荐的两条绕路：在插件里直接向宿主的接口发请求（要自己拿端口和口令，不是 v2
推荐的做法）；把 forge 的 v2 入口改走 effect 接口（那套接口的类型里有作业接口，但
这是一次大得多的迁移，不该为这一件事做）。

要不要给宿主提一个请求，请他们在 promise 适配层也暴露作业接口——由你定，对外发声
是你的授权域。

### D5 草稿期禁止派发（默认：保留，让权限带也拦原生 `subagent` 的调用）

plan 在草稿期禁止写，也禁止派发——否则派出去的工人替它把写了。换到原生路，
派发不再经过插件的 `task`，这条禁令只剩权限带这一道可以执行。默认做法：让权限带
对原生 `subagent` 的调用执行同一条禁令，拒绝文案不变。它现在**不拦**：〔沙箱〕plan
在草稿期，父会话调原生 `subagent` 照样建出了子会话；〔源码，forge〕禁令是按写类
工具名单判的，名单里有 `task`、没有 `subagent`。所以这一项不是“保留”，是要新加
一条判定。（对照的那一步没拿到结果：同一个父会话被要求调插件的 `task`，它 45 秒
内没调，原因没记录。草稿期拒 `task` 是现行的行为，由原来的草稿门测试管，不在这里
重证。）

这和已经撤掉的 change #2 不是一回事：change #2 要给原生派发加的是派发门（分区、
形状、池归属、crew 待定与合规）；D5 拦的是“plan 草稿还没批准时不能派人去干活”，
是 plan 自己的安全互锁。如果你认为草稿期也该允许原生派发，这项改成不拦，实现上
更简单。

### D6 工人在原生路上不能提问（默认：把封印写进工人代理文件）

来龙去脉见 Context。默认做法：插件编译工人代理文件时，把 `question: false` 一并
写进 `tools`（`src/roster-compile.ts` 的 `toolsFaceFor`，加一行）。宿主归一配置时
会把 `tools` 里的 `false` 变成对应动作的拒绝（〔源码，宿主〕
`core/src/config/normalize.ts` 第 539–550 行），和宿主给内建 `general` 盖的印是同
一种。〔沙箱〕一个 `tools` 里写了 `question: false` 的代理，原生派出后答的是“没有
提问工具”，没调任何工具（只跑了一次）。

只在 v2 上加，所以同一份配方在 v1 和 v2 上编译出来的工人文件会差这一行。v1 入口
原样不动——v1 的同步派发允许孩子提问（你当时在场），这是现行约定，不在这次改。

不选的另一条：让插件的权限带对所有带 `parentID` 的会话拒绝 `question`。好处是连
不是 forge 的自定义代理也盖到；但权限带在孩子会话里是不是每条工具调用都过一遍，
〔未验〕。你要是更想要这一条，告诉我。

### 定下来的做法（不需要拍板，列出来防止以后搞错）

- 派发：模型直接调原生 `subagent`；forge-\* 工人就是宿主眼里的普通代理预设。
- 工人不能再派下级：宿主的深度检查和归一后的 `subagent` 拒绝各守一道（见 Context，
  〔沙箱〕已实测）。
- 工人代理文件的描述和正文改成新写法：不再写“用 `task` 工具派发”。
- 完成通知、重启续跑、读子会话、续发消息：全部用宿主的。
- 每次派发完成只叫醒父会话一轮（插件不再补发）——代价见 Risks 第一条。

## Risks / Trade-offs

- **插件补发的唤醒没有了，包括宿主给不了的那部分。** 插件现在除了重复的那条，还会
  在宿主给不了结果的场合（中止原因、结果流丢失）补发唤醒。原生路上派发不经过
  插件，这些唤醒都不会再有。宿主自己通不通知：〔沙箱〕取消和异常结束两种都通知
  了，也都叫醒了父会话（见 Verification ⑤）。没测的：真实的上游超时或限流造成的
  异常结束（沙箱里是用“模型不存在”造的）；同时打断多个孩子时父会话被叫醒几轮。
- **看守不再覆盖原生子会话。** 插件的“结果流丢失”这类判定随之消失（少一种误判的
  来源）；但按同样的道理，子会话失联时也不再由插件兜底（推断）。crew 有规格里
  “原生子会话在飞”那道门兜着；非 crew 的派发靠宿主。
- **`/forge stop` 停不干净一小块**（D4）：已收工的非 forge 子会话，名下宿主自己的
  后台命令停不掉。宿主以后要是把作业接口也暴露给 promise 适配层，这一条就能补上。
- **顺序错了会“报假完成”。** 先取消工人的 forge 作业、后打断，工人会被自己那次
  轮询叫回来，接着把回合跑完、照常交报告，父会话收到的是“已完成”（〔沙箱〕试出来
  的）。所以 `/forge stop` 必须先打断、后取消作业。
- **带宿主后台作业的孩子会“复活”。** 只打断一个已收工、名下还有宿主后台作业的孩子
  是空操作；命令跑完，孩子被叫醒再答一轮，父会话再收到一条“已完成”（〔沙箱〕）。
  这就是 D4 那个残缺口在时间上的样子。
- **工人会卡在提问上**（D6）：不盖印的话，原生派出的工人一提问就没人答。
- **没有同步派发了。** 原生只有后台。你已经明确不要同步派发。
- **没有并发上限和排队。** 一次派出多少个由模型和你决定，插件不再限。
- **crew 编排者必须是主会话**（深度上限 1）。这和现状一致（工人本来就当不了
  编排者）；以后要嵌套，调宿主的 `experimental.subagent_depth`。
- **v2 的行为和 v1 分叉。** v1 入口原样不动，所以同一个插件在两类宿主上的派发
  行为不同。README 要写清楚。

## Verification（沙箱里已跑）

口径：宿主 2.4.0（沙箱服务，进程号 39988），forge 构建的 sha256 是 `f767eedbe8015a66…`
（版本号 0.34.1），UTC 2026-11-24 22:49–23:44。每个探针有一份结论文件
`nd-<探针>-<时间>-verdict.json` 和同名日志，原件在临时目录，副本归档在工作区根的
`archive\2026-11-25-d-native-probes\` 里。下表的数字和原文都是从结论文件里读的。
父会话都是 `forge` 会话；建过的会话，探针结束时都注销了。

| 件 | 做了什么 | 结果 |
| --- | --- | --- |
| ② 续用 | 同一会话先后调两次原生 `subagent`，第二次带 `sessionID` | 过：孩子还是 1 个；孩子对话里多了第二句；答的是那个词；没报找不到会话 |
| ③ 深度 | 让子会话自己调原生 `subagent`（跑了两次） | 过：允许调原生 `subagent` 的子会话去调，报的就是 Context 里那句原文，孙子会话 0 个。内建的 `general` 和 forge 工人当孩子时没调任何工具，直接答“没有这个工具”——这是孩子的回答，不是宿主的事实 |
| 今天的 `/forge stop` | 两个原生子代理正在忙时调它 | 回 “No async dispatches in flight for this session … nothing to stop.”；两个孩子照样忙 |
| ④ 取消·forge 工人 | 两个孩子各有一个长的 `forge_shell` 作业；一个先打断后取消作业，一个先取消作业后打断 | 先打断：回合中止，父会话立刻收到“已取消”，插件的作业进程还在，取消作业后才消失。先取消作业：工人被轮询叫回来，**接着跑完、报告完成**，父会话收到“已完成”；之后再打断是空操作 |
| ④ 取消·`general` 前台命令 | 孩子回合里跑一条宿主前台长命令，打断它 | 回合中止；5 秒后命令进程消失；工具报 “Command interrupted by the user”；父会话收到“已取消”并被叫醒 |
| ④ 取消·`general` 后台命令 | 两个孩子收工时名下各留一个宿主后台作业 | 只打断：空操作，进程还在，命令跑完孩子被叫醒又答了一轮，父会话收到“已完成”。再取消宿主的作业（探针直接调宿主的实验接口，插件调不到）：5 秒后进程消失 |
| ④ 补·删子会话 | 对已收工、带宿主后台作业的孩子，直接调宿主的删除接口 | 作业跟着没了（命令 16 秒时死，本该跑 60 秒）；父会话没收到任何通知、没被叫醒 |
| ⑤ 通知 | 取消一个孩子；让另一个异常结束 | 取消：父会话 3 毫秒内已有“已取消”，被叫醒，孩子记为 `interrupted`。异常结束（把孩子的模型换成一个不存在的，续发一轮才失败）：孩子记为 `failed`，父会话收到 `error` 通知、正文是报错文字，并被叫醒。两种都没有“把没跑完的报成已完成” |
| ⑤ 补·长命令 | `general` 孩子跑一条 150 秒的宿主前台命令，只看不打断 | 命令跑着的时候孩子一直忙（10 次采样都是），没自己转成后台；156 秒时命令结束，孩子收工，父会话收到“已完成” |
| D5 草稿期 | 父会话写下 plan 草稿，再调原生 `subagent` | **没拦**：调用成功，建出了子会话 |
| D6 提问 | 让三种孩子各调一次提问工具 | forge 工人：调了，一直挂着，40 秒后被探针打断；打断后工具报“被打断”，父会话收到“已取消”。`general`：没调，答“没有提问工具”。代理文件里写了 `question: false` 的：没调，答“没有提问工具” |
| 目录 | 父会话在两个新建目录和主沙箱目录里，各原生派出子会话，让孩子报自己的工作目录 | 子会话记录里的目录都和父会话一字不差（3 次）；`general` 孩子用宿主 shell 跑出来的路径（2 次）、forge 工人的 `forge_shell` 作业的 `cwd`（1 次）也都是它 |

还没验的（动工时补；哪一条的结果和这份草案对不上，先回来改）：

- 真实的上游超时或限流造成的异常结束，父会话收不收得到通知；
- 同时打断多个孩子时，父会话被叫醒几轮；
- 回合没结束的孩子名下有宿主后台作业时，打断会怎样；正在回合中的孩子被删会怎样；
- 插件接口里的 `session.remove`，和直接调宿主的删除接口是不是一个效果；
- 权限带在孩子会话里是不是每条工具调用都过一遍；
- effect 接口运行时通不通。
