# Proposal: dispatch-resilience

## Why

Five production pains in the dispatch pipeline, each with reproduced evidence — this change is the umbrella for fixing all of them systematically, fold by fold, each fold with its own closed loop (deterministic tests + live sandbox replay on the published build):

1. **Headless hang** (acute, reproduced twice — 2026-11-15 47621 round and the 0.23.3 F23 round): a forge-family worker calling `forge_shell` in serve mode hangs FOREVER at the two-piece permission gate (`plugin.ts:1640` — plugin tools bypass permission evaluation, so `context.ask()` fires and the injected ask rule waits for a dialog nobody answers). The child sits at `forge_shell:running` indefinitely. The root cause is deeper than a missing dialog: the config hook rewrites EVERY non-deny posture — including an explicit user `allow` — to `ask` (`plugin.ts:3427`), and the permission.ask belt rewrites it again (`plugin.ts:3910`), which is exactly why `"permission": {"forge_shell": "allow"}` in config does NOT help. Fixing fold A therefore includes the plumbing: a pre-rewrite config snapshot so explicit user config can actually reach the gate.
2. **Hung children hold cap slots forever**: nothing watches a dispatch CHILD's liveness. The watchdog (hang-watchdog spec) covers stall of forge_shell COMMAND processes, not dispatch sessions. A child stuck busy-but-silent (e.g. a wedged model call) occupies one of the 3 async cap slots indefinitely with no intervention. User decision: adopt omo's activity-stale AUTO-KILL mode (explicitly overriding the earlier non-destructive preference).
3. **Dead children are never retried**: a child that dies of a provider/transport error simply ends as an error wake; the parent must notice and re-dispatch manually. Our children work on a SHARED workspace — a fresh child sees partially-modified files on disk and can continue from where the dead one stopped (user-confirmed resume model), so automatic respawn with a resume preamble is safe in this codebase's workflow.
4. **The async cap hard-refuses** at 3 running per session: the parent must pace waves by hand (human-in-the-loop — the user finds this tedious). omo queues beyond its concurrency limit and slots free up automatically.
5. **Host restart orphans running children**: the dispatch registry and pollers live in process memory. After a restart nobody tracks the running child, the final report is lost, and the parent never learns (crew sessions survived on disk+git signal backstops). The user clarified that what matters from omo's design is NOT the event itself but PERSISTED task records that make recovery possible. Provenance note: omo's own background-agent registry is in-memory (`globalThis`, prompts redacted) and persists nothing — the journal here is a NOVEL mechanism, not a port; the in-repo precedent is job-supervisor's persisted survival registry + next-host-start orphan scan, which this design cites and cross-references.

## What Changes

Five folds under one umbrella, delivered and released one at a time:

- **Fold A — headless ask liveness** (spec: `tool-partition`): the forge_shell two-piece permission gate learns to resolve headlessly. When the host runs headless (serve mode, auto-detected, or forced via env), a forge_shell call whose posture would ask is resolved WITHOUT a dialog by the existing exec classifier (`src/exec-classify.ts`): READ-class commands proceed, WRITE-class commands are refused with an honest error the child can adapt to and report. Explicit user config (allow/deny) is always honored first and never overridden. User-confirmation doors (plan_approve / plan_close / goal_* / crew_close asks) are NEVER auto-resolved — they remain real dialogs.
- **Fold B — activity-stale reap with auto-kill** (omo mode, user decision): a RUNNING dispatch child with no activity advancement (`session.get` `time.updated`) for `FORGE_DISPATCH_STALE_MS` (default 2700000 = 45 min) past a 60 s minimum-runtime floor is reaped: activity double-check (a re-read showing a refreshed timestamp resets the timer), existence probe when the status map is unhelpful, then SDK abort and an honest terminal wake (`stale: aborted after N min without activity`). The reaper is config-switchable to observe-only (notice without kill).
- **Fold C — retry with resume preamble** (user decision): a child that terminates in a RETRYABLE error (provider/transport class per a ported error classifier) is respawned automatically: same agent, original prompt plus a resume preamble instructing the new child to inspect current workspace state first and continue rather than redo. `FORGE_DISPATCH_MAX_ATTEMPTS` (default 2 = 1 retry), fixed 10 s backoff, attempts surfaced as progress notices. NOT retried: stale kills (a hang would be re-hung), user aborts, textless-idle floor findings, deterministic refusals (partition/gate/permission). Exactly one terminal wake still — retries are internal.
- **Fold D — cap queueing** (omo mode, user decision): beyond the 3-running cap, async dispatches enter a per-session FIFO queue (bounded 10, honest refusal beyond) instead of failing. The call returns a queued handle immediately; a queue pump spawns children as slots free; gates (pool, crew, partition) evaluate at CALL time and the roster is re-checked at spawn time; owner death flushes the queue; a queued dispatch that starts emits a progress notice.
- **Fold E — persisted dispatch journal + restart recovery**: every dispatch record (jobId, owner, agent, child session, description, prompt, attempts, state, timestamps) is appended to a bounded workspace journal (`.opencode/forge/dispatch-log.jsonl`, rotated). On plugin init, records in a running/queued/retry-pending state are re-probed: child alive → tracking re-armed; child finished while the host was down → final message fetched and the wake delivered; child gone → honest terminal. Restart no longer orphans children.

Fold order: **A → B → C → D → E** (A first: it is acute and independent; E last: the journal schema benefits from all record fields existing). One release per fold, each with deterministic tests + live sandbox replay. Declared umbrella strategy: the SPEC archives only at umbrella close (section 6), so each per-fold release intentionally deviates from the live spec until then — accepted, documented here.

## Impact

- Specs: `tool-partition` (ADDED headless ask liveness requirement); `forge-subagents` (MODIFIED "Dispatch lifecycle (wake, cap, harvest)" — the cap-refusal scenario becomes queueing; ADDED "Dispatch resilience" requirement covering stale reap, retry, and restart recovery); `job-supervisor` (MODIFIED "Permission posture preserved" — the explicit-allow carve-out that makes fold A implementable).
- Code: `plugin.ts` (gate headless resolution, dispatch site, queue pump, recovery scanner), `src/dispatch-async.ts` (stale tracking, error classifier port), `src/exec-classify.ts` (reused, maybe extended), new `src/dispatch-journal.ts` (persistence), new `src/dispatch-retry.ts` (classifier + policy), tests for every fold.
- Users: workers can no longer hang headlessly; hung children are reaped with honest wakes; provider-error deaths self-heal with resume semantics; waves can exceed 3 running without human pacing; restarts no longer orphan children or lose reports.
