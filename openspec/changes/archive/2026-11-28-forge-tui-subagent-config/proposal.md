## Why

Forge 0.35.0 now dispatches native OpenCode V2 workers, but configuring them still requires hand-editing JSONC, finding model identities and reasoning levels, and synchronizing the native projection. Bring the configuration experience into the host TUI, borrowing OpenChamber's entity editor and catalog-driven selection without creating a second configuration system.

**Revision (2026-11-27, probe-driven, drafted pending user approval; approved and apply-authorized 2026-11-27 — see the approval record in What Changes):** the original write path assumed TUI-side same-host proof. Terminal probes (archive `2026-11-27-forge-tui-subagent-config-probes` REPORT §8–§9.10, event evidence re-verified against raw `event-probe.jsonl`) proved the 2.4.2 TUI cannot observe its actual connection endpoint (the loopback-baseURL leg of the four-gate write gate is unsatisfiable), while the official Plugin RPC is fully functional in the real TUI: `ctx.client.rpc(def).echo` round-trips a nonce (`RPC_ECHO_OK nonceMatch:true`, version 2.4.2), unknown methods are rejected (`rpc.method_not_found` family), a single `await registration.dispose()` makes the method unavailable, `session.moved` events reach the TUI plugin with the new location and the host store/`client.session.get` reflect it, and default per-boot auth rotation means a restarted server is unreachable for the old TUI (401 retry storm, zero `server.connected`). The write architecture is therefore revised to server-mediated commit over the official RPC.

**Revision (2026-11-28, UX round):** production use of the delivered build by the user is recorded as user-experience acceptance of **basically usable** — it is NOT a claim that formal acceptance (sandbox gate ③, npm install gate ④, or all tasks) has passed. ### Commit protocol and trust boundary (summary; full contract in design/specs)

- Server-side prepare/preview step is pure-read and issues a bounded, short-lived, single-use token bound to the exact recipe target, scope and sessionID (including null), authoritative anchor/owner, original bytes + file identity, canonical patch + preview hash, and the server epoch/registration generation (the only server-provable epoch — the server has no client identity and cannot recognize a specific connection). The server never accepts an arbitrary absolute path or arbitrary write text; anything not covered by a valid unspent token is refused.
- The atomic commit re-verifies, under the server's commit lock, the snapshot taken at edit start and the confirmed scope before writing; multi-entry first creation commits with the create kind; entries a validator rejects are not written. Cancel and no-op never write.
- Server restart or a change of the RPC registration generation refuses all previously issued tokens (server-provable). The TUI, on detecting any disconnect, drops its in-flight tokens and opens a fresh editor session requiring new prepare and confirm (a client-instance protocol discipline, not an attestation). The server does NOT claim that a network disconnect alone voids its in-memory tokens within the same server process/generation — it cannot detect arbitrary transport reconnects; the honest residual is that API clients holding a valid unspent token can call within that epoch. An ambiguous commit outcome (missing receipt, crossed restart) is UNKNOWN: no persistent receipt store exists (receipts are same-epoch, in-memory), and current bytes matching the patch do not prove whether an old commit wrote — bytes are only ever used to build a new preview/sync, so a commit is never blindly replayed; the client re-prepares against current content and re-confirms, or syncs current state. No cross-epoch exactly-once promise is made. A sync failure after a successful save offers an independent retry that re-reads the current recipe, re-scopes and re-confirms; it never replays the old patch.
- Trust boundary, stated plainly: registering an RPC method is not a tool and does not attest a human origin. Any client holding the server's API auth can prepare and commit directly without any human in the loop; what the server guarantees is that writes stay bound to server-resolved targets and server-issued prepared tokens — displaying the preview and obtaining human confirmation is the TUI's responsibility, not a server-side guarantee. The human TUI remains the normal, only surfaced save entry and exposes no AI tool.

## Capabilities

### New Capabilities

- `forge-tui-subagent-config`: native TUI navigation, scope-aware forms, host model choices, explicit safe recipe changes and deterministic synchronization — executed through the server-mediated RPC commit protocol.

### Modified Capabilities

- `forge-subagents`: narrow exception to read-only recipe ownership for explicit human TUI saves (executed by the server's forge-config RPC handlers under the forge-tui-subagent-config commit protocol); explicit TUI synchronization alongside existing in-band sync and auto opt-in.
- `command-surface`: distinguish the existing single server `/forge` family from the new UI-only `/forge-config` entry without restoring retired server commands.
