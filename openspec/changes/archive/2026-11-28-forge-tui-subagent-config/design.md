## Context

The archived `retire-plugin-runtime` change and Forge 0.35.0 are the code baseline. `src/forge-config.ts` has the exclusive `createPoolResolver`, shared upward discovery and fail-soft validators; the older `createForgeConfigLoader` still merges and is not the authoritative pool resolver. `src/roster-compile.ts` owns the native projection and no-clobber planning; `plugin.ts` wires `runRosterSync` and `forgeSyncTool` and keeps the in-process authoritative anchor state (`hostAnchors`/`v2HostAnchors`, `sessionMovedAnchors` at plugin.ts:296-335). The server package currently has only its root and schema exports.

**Probe baseline (2026-11-27, archive `2026-11-27-forge-tui-subagent-config-probes` REPORT §8–§9.10; key events re-verified against the raw sandbox `event-probe.jsonl`, masked output only, serve.log credentials never read):**

- The 2.4.2 TUI cannot observe its actual connection endpoint (`ctx.client` exposes no endpoint property; `config` is an API namespace) — the loopback-baseURL leg of the original TUI-side same-host write gate is unsatisfiable, so that gate fail-closes every write path. It is deprecated as an architecture premise (D2) but its probe history stays in tasks 1.3.
- Official Plugin RPC is real and functional on 2.4.2: server `ctx.rpc.register(definition, handlers)` returns a registration with `dispose()` (installed `@opencode/plugin` `dist/promise/plugin.d.ts` `rpc: RpcDomain`, `dist/promise/rpc.d.ts`); TUI `ctx.client.rpc(def)` yields per-method callables with `{location?}` call options and `events.on/subscribe` (`@opencode/client` `dist/promise/rpc.d.ts`); `@opencode/schema` `Rpc.define` accepts plain JSON Schema so no new dependency is needed. Probe-proven in the real TUI: echo round-trips a nonce (`RPC_ECHO_OK nonceMatch:true, returnedVersion:"2.4.2"`), an unknown method is rejected (`"Unknown RPC method: …"`, `rpc.method_not_found` family), and after a single registration `await registration.dispose()` the next call fails (`"RPC is unavailable: …"`). The earlier "dispose survivor" observation is explained by multiple setup runs stacking registrations in one process (REPORT §9.8.3, hypothesis supported by round contrast); server-internal call options forbid `location`/`headers`, i.e. server-side calls stay within the same server.
- The real TUI plugin receives `session.moved` (`dataKeys [location, projectID, sessionID, subpath]`, location = move target, ~20 ms after the event); the host store already holds the new location before an explicit `sync` (REPORT §9.8.1 erratum), and `client.session.get({sessionID: full})` returns the direct row with the new directory (REPORT §9.10.1). The server plugin has the same event seam (`sessionMovedAnchors`, plugin.ts:296-335) and it remains the only live authority because the plugin-facing `session.get` lags pre-move locations.
- Default per-boot server auth rotates on restart: the old TUI retries with stale credentials into a 401 storm with zero `server.connected` events (REPORT §9.10.3). Lossless reconnect is NOT claimable; RPC events are live-only per the upstream document (`services/site/src/docs/content/build/plugins/rpc.mdx` @ v2.4.2 — the live page is a 404 and is not cited as an online source), and event replay is not guaranteed.
- Probe-path-only: a dynamic import of the RPC schema module crashed the probe host (`Object.values Die`); recorded as probe-path fact, not a general claim — statically bundling the definition object is a deliberate design choice, and the probe does not prove dynamic import universally fails.
- The HTTP surface requires `{input: {...}}` wrapping on `/api/rpc/{id}/{method}`; the SDK `client.rpc` call auto-wraps (REPORT §9.7 contract erratum).

OpenChamber's Agents settings and SettingsView still provide the interaction precedents (directory-scoped entity lists, catalog-driven model selection, save feedback); Forge adopts the ideas, not the Web implementation, storage or autosave. The V2 TUI entry, palette/slash registration, dialogs and keyboard are probe-proven; the narrow layout remains pending (tasks 1.1).

## Goals / Non-Goals

**Goals:** a human-only, host-native configuration entry sharing the existing recipe ownership, validation, compiler and host registration contract; all writes executed by the server plugin through the official Plugin RPC under a bounded prepare→confirm→commit protocol; deterministic tests plus real TUI proof.

**Non-Goals:** model-visible recipe editing APIs, a second registry/configuration file, a new dispatch engine, changes to harness behavior, arbitrary host config editing, direct rename or new recipe fields, a lossless-reconnect or caller-is-human guarantee, a self-made HTTP endpoint or `service.json` fallback.

## Decisions

### D1 — Native TUI entry, separate from server

Unchanged: expose the existing `/forge` server family unchanged and register the `Forge: Configure subagents` palette entry and `/forge-config` only in the TUI (`./tui` export of the same package), with native searchable selections, dialogs, theme and compact narrow-terminal fallback. If native entry cannot load, do not break server setup or fake a server command as replacement.

### D2 — One recipe authority; the server adjudicates ownership (same-host gate deprecated)

The recipe authority, resolution algorithm and compiler stay exactly where they are (`createPoolResolver`, `discoverProjectFileWith`, `forgeConfigPaths`, `parseForgeJsonc`, `validateAgentSet`, `validateOverrideNode`, session anchor resolution in `plugin.ts`) — not a second precedence algorithm. What changes is where the editor's questions are answered: the TUI no longer adjudicates ownership itself. Ownership, scope, exact owning path and namespace are resolved by the server's RPC handlers from the server's authoritative state (host anchor registry, `sessionMovedAnchors` including its live `session.moved` record, known workspace families). The TUI-side four-gate same-host proof (forge row active, `/api/info` PID/hostname, loopback baseURL, nonce fs read-back) is deprecated as a write premise — probe-proven unsatisfiable on 2.4.2 — and replaced by server-authoritative ownership plus preview binding. Still forbidden: `service.json` connection fallback, self-made HTTP endpoints, model-callable write tools, a second recipe resolver. A missing project recipe may be created only at a server-verified workspace root with a valid declared pool and explicit fallback warning; global creation requires explicit confirmation of the exact global path and machine-wide scope; unselected built-ins are never activated. Revalidate server Forge active state and RPC provability before any operation; disabled, absent or unverifiable server Forge (or an unprovable RPC transport) means zero writes and zero syncs, including retries. Global overrides remain global and a generally independent scope; never infer the anchor from TUI cwd.

### D3 — Catalog and draft isolation

Unchanged: observed host provider/model availability and per-target model metadata via a narrow adapter; `variant.list/set` never treated as an arbitrary target's list; missing metadata disclosed as unknown; Auto/Pinned as an atomic draft-level pair; raw unknown values preserved in unchanged fields; existing validators and materialization semantics; no availability registry or fallback list.

### D4 — Draft in the TUI, commit on the server (prepare → preview → explicit confirm → atomic commit)

The TUI owns drafts, forms, dialogs and confirmation only; it never writes a connection-observed path as a local file and never derives a local path from a remote target. The write itself is a server-side protocol:

1. **Prepare (pure read).** The edit-start snapshot is the original bytes and full file identity the server reads exactly once, when the editor opens the target, issued as a snapshot handle; the TUI drafts against that handle and the prepare request references it. The server re-resolves the authoritative target (scope, sessionID or null, owning file, anchor/owner), computes the canonical patch and preview hash against the handle's bytes — never a fresh read at prepare or commit time, so an external edit between form open and Save is refused (reload) instead of silently swallowed — and returns the preview for display (exact file, diff, scope). No write occurs; the prepared state lives in server memory as a bounded, short-lived, single-use token that binds: recipe target, scope + sessionID (including null), authoritative anchor/owner, the edit-start snapshot's original bytes + full file identity, canonical patch + preview hash, and the server epoch/registration generation. The token lifetime is a bounded implementation parameter returned as `expiresAt`; expired tokens are refused and require a fresh prepare (tested with an injected clock, no auto-renewal). A `sessionID: null` scope means exactly the home scope of the server-observed location at prepare time — location A's home on this server plus the server's own global home — never a wildcard, and the token's scope binding includes that observed location: on the same server, a token prepared under location A is refused when the target now resolves under location B, even when the global target path is identical (the binding is the location, not the server home path itself). Cross-instance and after-restart/registration-change refusals are covered separately by the epoch binding. The server has no client identity: it cannot bind a token to "the connection that issued it", and the only server-provable epoch is the server epoch/registration generation. The server never accepts an arbitrary absolute path or arbitrary write text — any request not resolvable to a server-owned recipe target or not covered by a valid unspent token is refused.
2. **Explicit human confirmation.** The TUI shows the preview (target file, scope, server-issued target identity, diff); only an explicit human Save & Sync action triggers commit. Cancel and no-op never write; prepare is pure read and cancel simply drops the token.
3. **Atomic commit (server lock).** Under the server's commit lock — one lock per actual target, shared across locations for a global target — the handler re-verifies, from the edit-start snapshot handle (the bytes and identity read once at editor open, never a fresh read): original bytes and file identity unchanged, pool ownership and confirmed scope still valid (second scope check after confirmation), then writes atomically (same-directory temp + exclusive publication as proven in `src/forge-config-edit.ts` tests), and returns a receipt (saved bytes/identity, per-entry outcomes). The receipt is in-memory and same-epoch only; there is no persistent token or receipt store. Multi-entry first creation commits with the create kind per entry; entries rejected by validation are not written and are listed in the receipt. Concurrency rules: a given token commits at most one write; two prepares over the same original bytes serialize — once the first commit succeeds, the second token's snapshot is stale and is refused; a sync step that fails still consumes the commit token (the saved recipe is recovered via the independent re-prepare retry, not token revival). Token lifecycle is deliberately minimal: tokens are valid only within their server epoch/registration generation and are at-most-once; when a receipt is missing or the server has restarted, the outcome is UNKNOWN — no cross-epoch exactly-once promise is made. Current bytes are never used to adjudicate an ambiguous old commit (matching bytes prove neither "written" nor "not written"); they only feed a NEW prepare or a sync of current state, so a client resolves ambiguity by re-preparing and re-confirming, never by replaying. The server's refusal surface is exactly what it can prove: tokens from before a restart or registration-generation change, unknown tokens, unspent/spent-state violations, and targets its authoritative set cannot adjudicate (where the authoritative host set cannot fully adjudicate a target, the dependent sync or change is refused rather than served from a newly invented registry; registration location and the anchor set are adjudicated separately). What the server cannot prove it does not claim: it cannot detect an arbitrary transport reconnect and does not void in-memory tokens on network disconnects alone — that residual is stated, not hidden (see D7). The human TUI is the only surfaced save entry; no AI-callable tool is registered for this protocol.

### D5 — Trust boundary stated exactly (no overclaim)

Registering an RPC method is not registering a tool: the RPC domain has no tool shape, no `/tool*` endpoint appears in the 2.4.2 OpenAPI, and the probe confirmed no new tool rows or event types after registration. But an RPC method is also not a human attestation: any client holding the server's API auth (the same credential the TUI itself must hold) can call the methods directly, shell out to them, or script them; a scripted client can prepare and commit without any human in the loop. The server-side guarantees are exactly: writes are bounded to server-resolved recipe targets, covered by a server-issued prepared token that binds the exact content (preview hash), single-use, valid only within the server epoch/registration generation, and receipted within that same epoch. Whether a human saw the preview is the TUI's responsibility, not a server-side guarantee. The protocol does not stop an authorized process from calling the API directly, and docs/UI must not claim human verification.

### D6 — Shared compiler and independent save/application receipt (server-executed)

`planRosterSync`, `executeRosterSync` and `runRosterSync` semantics are reused server-side behind the RPC sync method — no separate compilation logic. Recipe persistence and native projection/application outcomes are independently reported. Applied status requires host confirmation of the actually changed observable fields (prompt/permission/variant where applicable) or the exact removed ID — an unchanged existing ID is not "applied", and an unobserved change is reported as unconfirmed, never applied. Before sync the server fixes the selected family identity with full before/after resolution; if coverage is unknown or the target owner moved, sync is refused (not guessed); a cross-family collision-winner change is disclosed only and never silently reconciled — the existing explicit host-wide sync recovery remains the separate authorization path. Hand-written files and other families are untouched (no-clobber, GC by marker). On sync failure after a successful save, the receipt stays and an independent retry re-reads the current recipe, re-resolves scope, re-prepares and re-confirms — it never replays a saved patch against the world. A commit response that is ambiguous (timeout, dropped connection) is never blindly replayed: the same-epoch in-memory receipt, where it exists, determines the outcome; without it the state is UNKNOWN and current bytes are never used to adjudicate saved/not-saved — bytes only ever feed a new prepare or a sync of current state. Running children keep existing semantics: Auto inheritance binds at dispatch, depth freezes per session, request-time model pin hot-applies; no interruption or restart.

### D7 — Epoch invalidation and honest reconnection limits

The server-provable epoch is the server epoch/registration generation: after a server restart or a change of the RPC registration generation (plugin reload/re-register), every previously issued token is refused. The server has no client identity — it cannot recognize "the same connection" across a transport break, so it does NOT claim that a network disconnect alone voids its in-memory tokens; within one server process/generation, the honest residual is that an API client holding a valid unspent token can still commit. The TUI-side discipline is client-instance protocol, not attestation: on detecting any disconnect (or any epoch change it can observe, e.g. version/pid/registration mismatch on echo), the TUI drops all in-flight tokens and opens a new editor session that requires fresh prepare, fresh preview and fresh human confirmation. Whether the transport layer detects every reconnect cannot be guaranteed; the promised recovery path is the normal one — the TUI re-reads current state, re-prepares and re-confirms. Because default auth rotates per boot, the design assumes nothing about automatic recovery after a server restart; the UI discloses the broken connection and the re-confirmation requirement. No lossless-reconnect claim and no cross-epoch exactly-once promise is made anywhere.

### D8 — RPC definition export and packaging

One `./rpc` export of the same npm package carries the static definition object shared by server and TUI (plain JSON Schema values, no new dependency; statically bundled by design choice — the probe-path dynamic-import crash is path-specific and is not generalized). The server registers handlers in plugin setup; the TUI calls through the current `ctx.client`. Probe-proven behaviors are regression anchors: nonce echo, unknown-method rejection, `await dispose()` → unavailable, re-register works. Events emitted by the registration (`registration.events.emit`) may carry progress; delivery is live-only and must never be load-bearing for correctness: correctness is resolved by the same-epoch in-memory commit receipt where it exists — a missing receipt or a crossed restart means UNKNOWN, resolved by re-prepare and re-confirm, never by replay; there is no persistent receipt store.

### D9 — Acceptance requires actual host proof (tasks discipline unchanged)

Local isolated probes before implementation; documented API (`rpc.mdx` @ v2.4.2 source, not the 404 live page) distinguished from observed behavior; if a required capability is absent, amend the OpenSpec with owner review before implementing a different user contract. The two release gates remain applicable; no inferred pass; historical unchecked migration tasks are caution, not proof. Existing pure-core test counts (e.g. `forge-config-edit.test.mjs` 54/62-pass runs) remain historical evidence of the editing core and must not be presented as new-architecture passes.

### D10 — UX round (2026-11-28, user-approved "可以的，改吧"): accessible layout, draft-overlay list, save-refresh continuity, compact feedback

Production user testing accepted the delivered build as basically usable (NOT formal acceptance) and approved a six-point UX plan. Decisions, with reconciliations to existing decisions:

1. **Layout (point 1).** Large and narrow terminals both get an accessible, keyboard-operable layout with short titles and layered fields (identity/mode primary, secondary fields below). List rows MUST NOT cram the full model identity into the title line — observed in the delivered build (`src/tui/entries.ts:146-181`, title and description share one line; main-controller Read).
2. **Edit page (point 2).** The entry page shows field controls with current values visible on one page, with direct access to the corresponding field editors (e.g. the prompt/permission editors) without unrelated navigation — a flat presentation, not a fully custom inline form. D3's atomic Auto/Pinned pair is a saved-recipe invariant, not a forced interaction step: changing the model of a Pinned entry keeps the mode and only revalidates the level (existing "Change a target model" scenario unchanged); the level is editable alone. The edit page's Save & Sync operates on the current pending batch and the confirmation explicitly enumerates the included entries — nothing outside the previewed batch is written (consistent with D4's preview binding).
3. **List overlay (point 3).** The list view merges ALL pending drafts over the base entries of the same scope. The delivered build merges only pending creates (`src/tui/flow.ts:393-418`, `if p.op !== create continue`; main-controller Read) — update/delete drafts are invisible. Overlay is presentation-only: pending values shown with a pending marker, delete shown as a removal marker, base file untouched until confirmed save. Search runs over the same merged view. Reconciliation with scope-aware browsing: "merge" here is same-scope draft overlay, never cross-scope (workspace/global stay unmerged). Discard reverts the view to base and MUST NOT pollute the edit-start snapshot used for conflict detection (D4 snapshot handle semantics untouched).
4. **Save-refresh continuity (point 4).** After a successful save the editor continues on a fresh editOpen — a new server-held edit-start snapshot per D4, not a protocol change. If that refresh fails, the UI reports saved + refresh failed, keeps the receipt accessible, and never replays the old commit (consistent with D6's retry semantics: re-prepare or explicit reload). The search query and current selection survive save/refresh within the same scope; this round's scope switch clears query and selection — a simple default, so no previous-scope context is carried into the new scope.
5. **Feedback (point 5).** Toasts are short summaries (counts + risk flags), never stacked long listings; the full receipt of any size is viewable on demand, paginated for large batches (consistent with the unit-closed 13-entry pagination work, which production feedback requires as the standard behavior); sync confirmation lists changed entries first plus an unchanged count; failures/unconfirmed/conflicts stay visible in both forms — brevity never hides risk.
6. **Unchanged bindings (point 6).** The two-step save and sync confirmations, every RPC security binding (D4/D5/D7), no-autosave and the commit protocol are not modified by this round; sections 6.x/7.x evidence and unchecked statuses stand untouched.

## Risks / Trade-offs

- TUI SDK drift → bind only probe-proven public interfaces; separate `./tui` and `./rpc` exports so the server remains loadable.
- Authorized non-TUI caller misuse → bounded single-use epoch tokens, server-resolved targets only, receipts; documented boundary: this constrains and audits writes, it does not attest humans.
- Server restart/auth rotation breaks sessions → no reconnect claims; tokens refused after restart/registration-generation change (server-provable); TUI drops in-flight tokens on detected disconnect; UI discloses and re-confirms from scratch.
- Ambiguous commit outcomes → same-epoch in-memory receipt when it exists, otherwise UNKNOWN resolved by re-prepare against current bytes (bytes never adjudicate an old commit); replay forbidden; no persistent receipt store, no cross-epoch exactly-once promise.
- Remote write scope expansion → user-visible disclosure of scope/path/server-issued identity; explicitly approval-gated in the proposal (approval obtained 2026-11-27); silent expansion prohibited.
- Global fallback surprises and stale scope → explicit source, current effective scope, create warning, server-side authoritative resolution and commit-time recheck.
- Concurrent editors or malformed JSONC → refuse stale or ambiguous writes, preserve unrelated bytes and show findings.
- Model metadata gaps → show unknown/unverified state rather than guessed variants; preserve existing custom values.
- Saved recipe but stale native registry → separate receipt and deterministic server-side retry; keep existing dispatch staleness gate.
- Narrow terminal → native compact keyboard-driven list/detail layout; verify in real TUI.
- UX round (2026-11-28): short toasts truncating risk disclosure → counts plus risk flags in the short form, full on-demand detail; draft overlay misleading the user → per-entry pending markers, base bytes untouched until confirmed save.

## Migration Plan

No migration of existing recipes or generated data. Publish the same package with the root, `./tui`, `./rpc` and schema exports only after local gate passes and explicit release authorization. Verify the supported CLI-only entry enablement and official installation; never automatically edit the user's main config, and avoid duplicate source loads. Removing the plugin or the TUI entry leaves recipe and existing server behavior intact; previous server-only builds can continue reading the unchanged recipe schema; TUI saves against an older server (no RPC) fail closed as unprovable RPC. Update the main forge-subagents descriptive Purpose to reflect the narrow human-save exception at the authorized archive step, not in advance of delta approval.
