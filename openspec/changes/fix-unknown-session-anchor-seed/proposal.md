# Proposal: fix-unknown-session-anchor-seed

> **草案（2026-11-24），等用户批准；立稿时没动代码。**
> 这是行为改动，不在任何已批准的 change 里。它修的是**现有规格已经写明、
> 实现却漏掉的一条接缝**：`forge-subagents` 的 “Session directory resolved
> per session on multi-location hosts”——会话的目录“永不取自最后初始化的目录”。
> 排期建议 0.34.2，排在 0.34.1 发布之后。真机宿主现在就是多目录状态，
> 这个缺陷当下就能触发。

## Why

宿主在一个进程里加载多个目录时，插件给会话定目录有两条路。**工具体**那条
是对的（0.33.1 修的）：事件自带目录 → 内存绑定 → 宿主会话记录 → 默认目录
（带提示）。**拦截带**那条漏了：权限评估和工具执行前的检查（草稿禁写、
状态文件边界、crew 待定）用 `stateForBan(会话)` 查会话，内存表里没有，就
拿 `hostWorktree`——**最后初始化的那个目录**——给这个会话建绑定。

于是，一个插件还不认识的会话，在它第一次调用写类工具（或发起插件的 `task`
派发）时被绑到别的目录；而内存绑定在工具体里排在宿主记录前面，所以之后每次
forge 调用都跟着错，也不会出现“用了默认目录”的提示，更不会自己改回来。
受影响的是插件的工具和检查（`forge_shell` 的工作目录、相对 `workdir`、计划 /
目标 / crew 记录、派发日志、池门）；宿主自己的 `write` / `edit` 按会话记录
解析路径，不受这个错绑影响。

“插件不认识的会话”比想象的常见。实测在宿主 2.4.0 上，会话创建并不会让
插件绑定它（刚创建的会话 1.5 秒后在台账里没有行；原因未查——事件未送达，
或载荷形状不符）。所以除了插件自己派发出去的子会话，**任何会话在第一次
调用 forge 工具或第一次空闲之前都是未绑定状态**。

| 形状 | 怎么触发 | 沙箱复现（0.34.1 构建，宿主 2.4.0） |
| --- | --- | --- |
| 重启后的旧会话 | 重启后第一个回合的第一个工具调用是写类工具 | arm3：绑到 B；不带 `workdir` 的 `forge_shell` 跑在 B，无提示 |
| 全新会话 | 新会话第一个工具调用是写类工具（不需要重启） | arm5：同上 |
| 派发被拒 | 未绑定会话调用插件的 `task`，派发在任何一道门前被拒 | arm4：调用者被绑到 B，一直留着 |
| 原生子会话 | 宿主原生的 `subagent` 工具派出的子会话——插件不参与创建，所以没有“创建即绑定” | arm6（3 次一致）：子会话的宿主记录写着目录 = A，创建时未绑定，第一次 `write` 时被绑到 B。调用者不受影响：原生派发本身不触发任何查会话的检查 |

（A = 会话自己的目录，B = 之后才初始化的另一个目录。）

真机（多目录宿主）2026-11-24 的两次事故都是这个机制：

- **09:59:09Z（北京时间 17:59）**：一个 `general` 子代理第一次 `write`，
  被绑到 `F:\…\SorenUnityLabs\.opencode\goal`——宿主 02:33:18Z 启动时它
  排在初始化顺序的最后；02:55Z 它已被驱逐，但内存里这个值 8 小时没换。
- **10:46:27Z（北京时间 18:46）**：本会话在新加载的模块里第一次 `edit`，
  被绑到 `F:\…\SorenUnityLabs`（当时最后初始化的目录）。

11-23 那次（review worker 被绑到 Unity 工程）也是同一机制。

## What Changes

- **拦截带不再用“最后初始化的目录”给未知会话定目录。** 多目录宿主上，
  拦截带（权限评估、工具执行前检查、crew 待定检查）遇到内存表里没有的
  会话时，按**宿主会话记录**解析——会话自己的目录，否则沿父会话链向上
  找——与工具体同一条链、同一种读法（经注册它的那次初始化自己的客户端）。
  查不到就让会话保持未绑定、照旧放行，绝不猜。
- **单目录宿主保留“启动目录播种”。** 单目录宿主上“最后初始化的”就是
  唯一那个，不会错；v1 宿主和单目录 v2 宿主的行为逐字节不变。
- **状态文件边界检查**：会话未绑定时，绝对路径照常检查，相对路径不再
  拿别的目录当基准。
- 不改：工具体的解析顺序；“默认目录”兜底及其提示（0.33.1 已批准的方案甲
  第 3 项）；插件派发时绑定子会话；v1 路径。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `forge-subagents`：需求 “Session directory resolved per session on
  multi-location hosts” 补上拦截带这条接缝的明确覆盖——每一条查会话的接缝
  （含权限带）都要先经宿主会话记录解析未绑定会话，不得绑到最后初始化的
  目录；查不到则保持未绑定并放行，不得拿默认目录顶替。新增场景把四种已
  复现的形状钉死，并钉死“别的目录里有草稿不会导致误拒”。

## Impact

- **代码**：`plugin.ts` 的 `stateForBan`（播种条件）、v2 两条拦截带里对它
  的调用（`tool.execute.before`、`permission.hook("evaluate")`）、crew 待定
  检查在带上的调用、状态文件边界的基准目录、插件 `task` 工具体里那次抢在
  重绑定之前的检查。加单测与变异检查；沙箱复现驱动（arm3/4/5/6）转成
  回归腿。
- **规格**：只动 `forge-subagents` 一条需求（MODIFIED，带全量场景）。
- **不影响**：v1 宿主、单目录宿主、npm 依赖、配置项、文件账本、工具接口。
- **相邻、但不在本 change 里（各自需要用户决定）**：
  1. 宿主原生的 `subagent` 工具与插件的 `task` 并存，而**插件对原生派发
     一道门都不查**。实测（沙箱，0.34.1 构建，宿主 2.4.0）：原生派发递到
     插件钩子时工具名是 `subagent`，插件所有派发门都按 `task` 写、写类清单
     里也没有它。直接后果——非 forge 的 `build` 会话用原生 `subagent` 派发
     forge worker **成功了**（子会话 agent = `forge-viewe2e-probe`，已回
     答），同一个会话改走插件 `task` 则被分区带拒绝；规格 `tool-partition`
     要求两者都拒。按同一条件判断、同样不被检查的还有：草稿期的派发形状
     门、会话域池门、crew 待定、crew 合规（这三项未单独做拒绝实验）。插件
     的派发引擎（派发日志、并发门、排队、唤醒、`/forge stop` 连带取消、
     创建即绑定）对这些派发也都不参与；真机派发日志 11-24 零行。
     **这是独立的行为改动**，另立 change `gate-native-subagent-dispatch`
     （同为草案），不在本 change 里。本 change 只保证它留下的子会话被绑到
     正确的目录。
  2. `plan-harness` 里“重启后禁写不再自动生效”那条场景，与现行实现
     （单目录宿主上经启动目录播种仍然生效）早就对不上；本 change 让多目录
     宿主与单目录宿主一致。是否改那条场景，留给用户。
  3. `hostWorktree` 另外两处与“会话绑定”无关的用法（读 `forge_shell`
     姿态配置、dispose 时按它恢复/收养派发）不在本次范围。
  4. 发版手册“升级前先隔离旧缓存副本”一步需要改成“先停宿主”（文档，
     不属本 change 的行为范围）。
