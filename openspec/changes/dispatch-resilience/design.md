# Design: dispatch-resilience

## Context

Five pains, one pipeline. Folds A–E each patch a distinct broken rung on the same ladder: a worker cannot even RUN headlessly (A); a running child can hang forever (B); a dead child stays dead (C); the 4th concurrent wish is refused outright (D); and a host restart forgets every wish in flight (E). omo (oh-my-openagent, `packages/omo-opencode/src/features/background-agent`) solved the same family at scale — the study from sync-timeout-notify carries over; this change adopts the four pieces the user prioritized, in omo's spirit but on our architecture. Provenance honesty (review F11): omo's background-agent registry is in-memory and persists nothing — fold E's journal is a novel mechanism; the genuine in-repo precedent is job-supervisor's persisted survival registry + next-host-start orphan scan, cited and cross-referenced below.

## Goals / Non-Goals

- Goals: headless workers get real answers instead of eternal asks (A); hung children are reaped automatically with honest wakes (B); provider-error deaths self-heal with resume semantics (C); waves queue instead of refusing (D); restarts recover in-flight dispatches (E).
- Non-Goals: user-confirmation doors are never auto-resolved (A); `opencode run` mode keeps its auto-reject ask semantics — it is NOT covered by headless resolution (A, review F9); no event-driven completion fast-path (latency-only — considered and rejected; the poller stays the guarantor); no change to the terminal-wake budget (exactly one final wake, whatever happens internally); no cross-session queue sharing (queues are per dispatching session); no provider management (retry reuses the SAME pinned model, no omo-style provider fallback ladders).

## Decisions

1. **Fold A — resolve the posture deterministically, and fix the plumbing that clobbers explicit config.** Headless detection is a STATIC property (host serve mode from `process.argv` — the plugin runs in the host process, verified; overridable with `FORGE_HEADLESS=1|0`); `opencode run` mode is explicitly NOT headless and keeps its auto-reject ask semantics (review F9 — otherwise scripted automation silently flips from always-reject to read-class-executes). The gate resolution order: (1) explicit user config first — which requires NEW plumbing, because today the config hook overwrites every non-deny posture (including explicit allow) to `ask` (`plugin.ts:3427`) and the permission.ask belt rewrites allow→ask again (`plugin.ts:3910`): the hook SHALL snapshot user-explicit values BEFORE rewriting, guarding against re-capturing the plugin's own injected `"ask"` on later config passes, and the snapshot feeds the gate — explicit allow skips the ask in BOTH modes (the single documented TUI behavior change, carried as a MODIFIED carve-out to job-supervisor's "Permission posture preserved"), explicit deny always wins (review F1); (2) TUI ask dialog unchanged for the default posture; (3) headless → the existing exec classifier resolves: READ-class proceeds, WRITE-class refuses with `[forge:headless-denied] <command head>`. The classifier is reused verbatim (`ExecKlass`/`classifyExecCommand`, exported; clean seam at the gate where `args.command` is in scope). Ordering vs the readonly-exec-seal: the seal finding lands FIRST (stronger, shape-specific refusal — review F20). User-confirmation doors are enumerated as exactly the non-exec `gate()` permission keys — `plan_approve`, `plan_close`, `goal_write (arm)`, `goal_complete`, `goal_resume`, `goal_discard`, `crew_close` — and never auto-resolved in any mode (review F2: `goal_discard` is a real gate door at `plugin.ts:1594`).
2. **Fold B — reap by inactivity, with omo's rails sharpened.** The activity anchor is `session.get`'s `time.updated` (part-level updates — a child streaming one long generation still refreshes it; a pure message-list re-read one tick later adds no independent signal — review F3); when no message has ever arrived the anchor is the dispatch start time. The `DispatchClient` seam gains `session.get` (currently absent, `dispatch-async.ts:48-73`); one call serves both the refresh rail and the existence probe (true omo parity: `session-activity.ts:18-22`). Rails: 60 s minimum runtime; pre-kill re-read (refreshed timestamp resets); existence probe (unresolved → skip sweep, missing → finalize). Abort-failure posture (review F3): a failed SDK abort with the session still existing skips the sweep and re-arms — finalization only when existence proves the session gone (omo `task-poller.ts:148-164`). Kill = honest terminal wake (`stale: aborted after N min without activity`) + ledger entry. `FORGE_DISPATCH_STALE_MODE` = `kill` (default) | `observe` (one progress notice per threshold crossing, no kill). Distinct from the textless-idle floor (0.23.3): floor = child GONE from the map with no reportable message; stale = child STILL BUSY with no activity advancement.
3. **Fold C — retry only what is transient, resume what is resumable, name the classes.** Vocabulary enumerated (review F4 — omo deliberately classifies provider-config errors as TERMINAL, never retryable, `error-classifier.ts:143-161`): retryable = transient transport/5xx/overload/rate-limit patterns; deterministic = provider-configuration, auth, model-not-supported, and contract error patterns (ported terminal classes) plus unknown — never retried (fail-closed). Call-time refusals (partition/gate/permission) throw before any child exists and are not a child-terminal surface — the deterministic scenario is pinned to child-terminal classes. Stale kills, user aborts, and floor findings are explicitly excluded (a hang re-hung is wasted work; an abort is a human decision; omo's stale timeout is likewise final, `task-poller.ts:169`). The respawn passes the ORIGINAL prompt plus the resume preamble (inspect-then-continue — the user's insight: children see the shared workspace). Mechanics: `FORGE_DISPATCH_MAX_ATTEMPTS` default 2, fixed 10 s backoff; the retry inherits the dying child's registry slot (the child died, the slot freed — no queue re-entry; queue-fairness questions move to fold D, review F15); dispatch-time policies (draft/crew mode-keyed denies, e.g. `questionDeny`) are re-applied on respawn; attempts surface as progress notices and the final wake discloses the attempt count; the once-budget is untouched. Fold ordering caveat: fold C ships before fold D exists, so its tests prove "retry keeps its slot" — queue-interaction tests live in fold D.
4. **Fold D — queue at the wish, spawn at the slot.** Per-session FIFO, bounded 10 (`FORGE_DISPATCH_QUEUE_MAX`), honest refusal beyond. The call returns immediately with a queued handle carrying `queued: true` metadata so the TUI task panel renders it (the panel keys on `taskId`/`sessionId`; a queued wish has no child session yet — the deferred creation is annotated, review F14). A pump spawns the queue head on every settle event (dispatch terminal / slot release). Gates: the pool/crew/partition belts evaluate at CALL time (unchanged semantics); at SPAWN time the re-checks are the target roster, the draft gate, and the crew belt (review F14c) — a tightening between call and spawn fails the wish as an honest error wake, never silently. Owner death flushes the queue (nothing to abort — no child exists yet) and terminalizes the journal's queued records. The "Concurrency cap" scenario keeps its title (delta rule) with queueing content; refusal copy lists in-flight AND queued ids.
5. **Fold E — the journal is the memory; init is the resurrection.** `src/dispatch-journal.ts`: append-only JSONL in the workspace (`.opencode/forge/dispatch-log.jsonl`, bounded at `FORGE_DISPATCH_JOURNAL_MAX` records, default 200). Rotation NEVER removes a non-terminal record (review F6 — never-die children can legitimately run for days; oldest-out count rotation would evict exactly the record fold E exists to protect): terminal records compact first, oldest first. Record fields per state; the original prompt is retained while a record is NON-TERMINAL — the journal is the only prompt source after a restart, so a queued record must carry its prompt to re-enter the queue and a running record must carry it to become retryable (review F6/N1) — and is redacted when the record terminates. On plugin init: non-terminal records re-probed per state (review F5 — queued and retry-pending need explicit branches; under a child-only reading both would silently cancel): `running` → alive: registry row + poller re-armed (stability fresh; notices resume); finished-while-down: `fetchFinalMessage` + wake delivered; gone: honest terminal. `queued` → owner session still resolves: re-enter the queue; else honest terminal + ledger. `retry-pending` → attempts remain: resume the retry (respawn); else honest terminal. Corrupt journal lines are tolerated (skipped) without aborting recovery. Recovery scope (review F17): the launch-anchor workspace is scanned at init; other workspaces recover lazily on their first session. Init trusts the journal and re-probes reality (session existence + status), so a stale record self-corrects instead of resurrecting a phantom. Cross-reference: this journal is the dispatch-session analogue of job-supervisor's persisted survival registry (which recovers surviving job PROCESSES via a next-host-start orphan scan) — separate ledgers, not cross-read.

## Risks / Trade-offs

- A: for WRITE-shape workers, headless enforcement IS the classifier plus its README-disclosed bypass surface (mutating scripts classified READ, `Start-Process` writers, encoded payloads) — a real relaxation from the always-ask TUI (review F10; the earlier "not a new trust boundary" claim was wrong for write-shape workers, where the ask dialog was the only gate). Mitigation: disclosed in the README and in the delta ("Unclassifiable commands flow headlessly" scenario); accepted by the user as part of this change's approval. Explicit-allow now skipping the TUI ask is a behavior change for users who set allow — that is the point of the carve-out (allow that silently meant ask was the bug).
- B: false-positive reap of a slow-but-alive child — mitigated by the `time.updated` refresh rail (covers long single generations, which a message-list anchor would not); 45 min default is far beyond any real pause; `observe` mode is the escape hatch.
- C: double-applied work for non-idempotent child effects (e.g. an already-made commit) — mitigated by the resume preamble (inspect-then-continue) and the attempt cap of 2; commit-like operations remain the child's judgment under the preamble.
- D: queued wishes whose roster/belts tightened while waiting — spawn-time re-check turns them into honest error wakes; queue depth 10 bounds memory and abuse.
- E: journal and registry can disagree (crash between transition and append) — init recovery TRUSTS THE JOURNAL and re-probes reality, so a stale record self-corrects instead of resurrecting a phantom.
- Umbrella: per-fold releases deviate from the live spec until the umbrella archive (section 6) — declared in the proposal.

## Migration Plan

Pure plugin change; the journal file is new and additive. Each fold ships independently (A → B → C → D → E), each with tests + live sandbox replay on its published build. Versioning decided per release (0.24.x expected given behavior breadth). Env-knob tolerance follows the shipped convention: invalid values fall back to the default; `FORGE_DISPATCH_STALE_MS` floors at the 60 s runtime floor (smaller values clamp to it) (review F21).
