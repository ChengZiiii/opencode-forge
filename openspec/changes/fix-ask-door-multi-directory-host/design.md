# Design: fix-ask-door-multi-directory-host

## D1 机制（实测推断；实施第一步先坐实）

- `v2Setup(ctx)` 每个目录初始化跑一次；`ctx.permission.assert` 是
  “这一次初始化所属实例”的接口。
- 插件把 `v2PermissionAssertFn` 放在模块级（`plugin.ts` 约 10315 行），
  每次初始化覆盖 → 所有目录的工具都调“最后那次初始化”的 assert。
- 确认请求登记在**被调用的 assert 所属的实例**上；终端客户端在**会话
  所在实例**里找待答请求 → 对不上就不弹。HTTP 驱动不带目录范围，
  所以照样查得到。
- 最后初始化的实例被收回后，那个 assert 直接抛错 → 所有目录一起失败。

**还没坐实的点**（所以任务 1 是坐实，不是直接改）：

- 宿主侧 assert 的会话查找规则（对照 2.4.0 源码逐行看一遍）。
- A 修复之后各几何的实测矩阵。旧探针（2026-11-23 21:29–22:11Z）打在
  A 之前，有几条腿被 A 的目录错位污染（“ws 会话已经有目标”其实是
  读到了第三目录的目标文件），不能直接当证据用。

旧探针与一次性补丁（归档用，不是实现）：
`view-e2e\logs\probe-door-*.json`、`probe-door-*.log`、
`spike-ask-closure.patch`。

## D2 按目录保存接口

```ts
// 每次初始化登记（同一目录再次初始化 = 替换）
const v2Inits = new Map<string, { seq: number; assert?: (input: unknown) => Promise<void>; live: boolean }>()
```

- `v2ToolContext` 的 ask 适配器改走 `askFor(sessionID, input)`：
  解析会话目录 → 取该目录条目的 `assert`。
- 取不到条目（会话目录解析失败、该目录从未初始化）→ 退到最新一次
  初始化的接口（= 现状），并记一行诊断日志（只进 forge 自己的日志，
  不进会话）。

## D3 目录被收回

- 宿主收回目录时不跑插件 dispose（已记账：C1 D1）→ 条目不会自己
  消失，只能靠“调用时发现失效”。
- assert 抛错且错误形状是“实例已失效”→ 该条目标记失效，退到最新
  **可用**条目重试一次；仍失败 → 原样抛出。失败关闭：任何一步都不
  产生“放行”。
- “实例已失效”的判定以宿主源码/实测的错误形状为准，不猜。

## D4 同病的其它接口（审计，不盲目改）

模块级、每次初始化覆盖的还有：`v2SessionRuleApi`、`v2SessionWaitSeam`、
`v2DispatchStorage`、`jobClient` / `anchorClientShared`（以及 v1 入口的
`hostWorktree`）。逐个确认两件事：是否按实例隔离、错了位有没有可见
后果。**只有坐实“按实例隔离且会错位”的才纳入本 change**，其余记进
待办，不顺手改。

## D5 不做

- 不改权限带决策表、不改门的名单、不弱化任何一道门。
- 不用绕过 ask 的办法（确认必须是真弹窗）。
- 方案丙（只写文档说明“多目录下不可靠”）不做——用户的真机就是
  多目录。

## D6 风险

- 会话目录解析失败时的降级必须仍能弹窗（最坏等于现状，不能更差）。
- 单目录宿主：登记表只有一条，行为必须逐字节不变（单测钉住）。
- 有头 TUI 那一腿要人工或驱动操作真实终端，沙箱到不了的部分按 D6
  记账，不冒充通过。

## D7 验证矩阵

{会话目录 = 最后初始化 / 不是} × {最后初始化的实例在 / 被收回} ×
{HTTP 不带目录 / HTTP 带会话目录 / 有头 TUI}。

- 新 E2E `21-ask-door-multidir-e2e.mjs`：HTTP **带会话目录范围**的
  listing 必须能看到待答请求（终端看的就是这一路）；修复前红、修复后绿。
- 有头 TUI：在“非最后目录”的会话里 `crew_close` 弹确认框，回答后
  才执行；回答前不执行。
- 单测：多初始化夹具下 ask 走对目录；目录被收回后失败关闭。
- 变异检查：去掉“按会话选接口”→ 多目录用例红；去掉失效降级 →
  收回用例红；单目录用例始终绿。
