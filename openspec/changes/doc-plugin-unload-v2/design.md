# Design: doc-plugin-unload-v2

动机见 proposal.md（Why）。这里只写怎么做，以及为什么不做别的做法。

## Context

- 仓库同时带两套入口：v1 的 `server`（插件函数，返回 `Hooks`，其中有
  `dispose`）和 v2 的 `default = { id, server, setup: v2Setup }`。宿主 2.4.0
  只用后者，且只读 `default.setup`。
- 清作业的代码（`exitCleanup.trigger("dispose")`、`jobManager.disposeAll(...)`、
  `watchdog.dispose()`、`sessions.clear()`）全部在 v1 的 `dispose` 钩子里。
- `v2Setup` 末尾返回的清理函数只做两件事：逐个调用本实例注册项的 `dispose`、
  中止自己的事件循环。
- 宿主 2.4.0 的驱逐端点对“手上有活”的目录：回 204，8 秒后目录仍在已加载列表
  里（2026-11-24T08:36Z 实测，作为事实记录，不作为断言）。空闲清扫驱逐则跳过
  “有活动执行或有宿主后台作业”的目录。

## Goals / Non-Goals

**Goals**

- 规格、注释、用户文档说的和宿主 2.4.0 上实际发生的一致。
- E2E 腿 D1 断言真实行为，验收门不再为它记账。
- 以后若宿主行为变了（比如开始调用清作业的钩子），这条腿要**变红**，不是
  悄悄继续绿。

**Non-Goals**

- 不把清作业代码接到 v2 清理函数上（方案甲）。官方设计与宿主自己的规则都是
  “作业比启动它的插件活得久”；接上等于在卸载时杀掉还在跑的活。
- 不删 v1 `dispose` 钩子。它是 v1 契约里活着的清理路径；本仓库没有 v1 宿主
  可验，不能凭“v2 上用不到”就删。
- 不给 2.4.0 写书面豁免（方案丙）。行为已经查清，不需要豁免。
- 不处理空闲清扫场景下的唤醒补送（见 proposal 的记账项 2）。

## Decisions

### D1 规格怎么写

需求段落里加粗的两句是这次的核心：`dispose` 是 v1 清理钩子、是插件卸载能终止
作业的唯一路径；v2 宿主上唯一的卸载清理只拆自己的注册、停自己的事件订阅，
不终止任何作业和派发行。场景拆成两条：v1 的“dispose 豁免派发行”（触发条件
改成 v1 宿主卸载），和新的“v2 宿主上插件卸载不终止任何作业”。

“任何插件卸载都让活着的作业继续跑”写成结果，不写成义务——义务是插件的
清理函数“不终止”，结果由它推出。

### D2 E2E 腿 D1 的通过条件

| 条件 | 为什么要有 |
| --- | --- |
| 驱逐请求被接受（204） | 场景成立的前提 |
| 发驱逐**之前**，子会话的 90 秒作业已经是活进程，并且发驱逐前一刻它还在 | 场景是“派发在飞时驱逐”。子会话还没起作业、或者没按脚本跑就回了话，驱逐就打在一段已经结束的派发上，“派发行没被碰”“作业跑到底”都无从观察。2026-11-24T19:45Z 的第一次主链就是这样：门变体不等子作业起来就发驱逐，记成了“派发行被碰”的失败 |
| 驱逐后 8 秒控制进程树还活着，并且跑到自然结束。必需的是**被驱逐目录自己的**那个控制作业；另一目录的对照作业起来了就算在内 | “没杀作业”的直接证据 |
| 驱逐**之前**腿内出现过 `v2 idle` 探针行 | **探针是活的**。没有这条，“钩子的探针行没出现”什么都证明不了 |
| 驱逐之后没有 `plugin dispose hook` 探针行 | 清作业的钩子确实没跑 |
| 驱逐后立刻：派发日志行仍是 `started`、无 outcome、子会话 200 | 派发行没被碰 |
| 台账里没有 `plugin dispose` 行 | 没有走击杀路径 |
| 恰好一次唤醒、带金丝雀、有 `Final report:`、无脚手架文案 | 派发正常完成 |
| 日志终态 `terminal` 且 outcome 不是 `aborted` | 同上 |

前提不成立 → 不算通过也不算失败。两条前提都在**驱逐之前**判：前提不成立的
腿跑完也得不出结论，没理由让它白等四分钟再重试。

- 探针不活：没有这条，“钩子的探针行没出现”什么都证明不了。
- 子作业不在飞：驱动最多等 240 秒让子会话的作业成为活进程，成为活进程后再等
  3 秒发驱逐。子会话没跑作业就结束了、等到头作业也没起来、或者发驱逐前一刻
  作业已经没了，都算这一条。

两种情况驱动都重试一次；两次都前提不成立，结论文件里记“结论不明”，到验收门
就是失败。结论文件新增两个字段：`childJobLiveBeforeEvict`（发驱逐前子作业
是不是活进程）和 `secondsFromDetectionToEvict`（从看到子作业到发出驱逐隔了
几秒）；驱动的通过条件把前者列为必需。

这条前提是 2026-11-24T19:45Z 那次判红之后补的。那一次的结论文件原样留档
（`view-e2e\logs\md-0342\run1-19h42Z-c1-premise-miss\`）：13 项事实为真，
唯独“驱逐后派发行没被碰”为假——子会话没跑规定的作业就回了话，驱逐后 8 秒
日志行已经是 `completed`。那是驱动的前提缺口，不是产品问题；补上前提之后
同一构建重跑通过（2026-11-24T20:03Z–20:13Z，17 项检查全真，从看到子作业
到发出驱逐 4 秒，一次通过、没有重试）。

“目录在驱逐后仍在已加载列表里”只记录不断言：它是宿主的行为，随宿主版本或
当时负载而变，和插件该不该杀作业无关。

### D3 验收门

`e2e-c1-D1` 只有通过和失败。通过 = 驱动 `pass === true` **且**七个事实都是
驱动自己记下来的：`hostContract` 里的六个（驱逐被接受、探针活着、控制进程
驱逐后存活并跑到底、钩子没跑、派发行没被碰），加上“发驱逐前子作业是活进程”
（`childJobLiveBeforeEvict`，记在 `hostContract` 外面——它说的是“场景成立”，
不是“宿主做了什么”）。这样一份只写了 `pass: true` 的旧格式结论文件、或者
一份没等子作业起来就发驱逐的旧驱动结论，都蒙混不过去。

### D4 单测

`tests/v2-setup-cleanup.test.mjs` 钉三件事：`v2Setup` 解析出的是函数；
它拆掉本实例的会话钩子和事件订阅；注册表里一个进程型作业和一条派发行在清理
之后原样还在。前两件是“这就是宿主会调用的清理”，第三件是“它不碰作业”。

**这里纠正过一次自己的假设。** 测试初稿断言“清理函数调第二次不会再拆一遍”，
全量单测跑了才红：清理函数的写法是每调一次就把每个注册项的 `dispose` 逐个调
一遍，本来就不是按可重复调用设计的；宿主 2.4.0 对一次获取只跑一次释放，所以
产品也不需要这个性质。改的是测试，不是代码：第二次调用的断言改成“不抛、拆完
的状态不变”。清理函数没动——“不改运行时代码”是本 change 的边界。

## Risks / Trade-offs

- **宿主升级后行为变化**：如果某个版本开始调用 v1 钩子对象，D1 会因为控制
  进程被杀而变红——这是想要的信号，届时改规格和这条腿。
- **v1 宿主未实跑**：依据只有类型声明和官方文档。写进了 proposal 的记账项。
- **空闲清扫场景未验**：见 proposal 的记账项 2。它不改变“卸载不杀作业”的
  结论，只影响“作业完成后的唤醒能否补送”。

## Migration Plan

没有运行时行为变化，无需迁移。随 0.34.1 发布（README 在 npm 包里，用户读到
的 “Plugin unload disposes the process-backed jobs” 改成分 v1 / v2 两种说法）。
