# Proposal: adopt-native-subagent-dispatch

> **草案，等用户过目（本地 2026-11-25 起草；同日先按沙箱实测改过一轮，又按同行对照和
> 一轮补充探针改过一轮）。代码一行没动；没批准不开工。**
> 这是四件事里 D 的落地约定。D 的方向已定：走原生（2026-11-25，用户授权我定）。
> 本页日期按本地时间（UTC + 8）。每条事实的出处只有四种，见 design 开头的说明。

定方向时用的是你的原话：

- “反正咱们现在在opencode v2上做迁移，那目的就是兼容opencode v2推荐的做法而不是打破它的优秀设计，否则很难做，我们最近一直踩的坑其实就是这个，v1能用的v2用不了”
- “理论上只需要实现forge stop能停掉subagent就行”
- “主代理中途读subagent还有给subagent再发信息…opencode v2本身应该都会做…现在不做未来也会做”
- 同步派发、并发上限加排队、按次授权，这三样不做了（你的表态，摘要）。

## Why

**现状是两套派发面并存。** v2 宿主上，forge 自己登记了一个叫 `task` 的派发工具
（沿用 v1 的名字，底下是插件自己的派发引擎：同步或后台、并发上限加排队、按次下发的
权限、派发日志、报告文件、进度通知、重启后的收养）；宿主自己另有一个原生的
`subagent`。模型两个都能调，两边的生命周期各管各的。

**调研报告当时建议保留 `task`**，理由是四样原生给不了：同步派发、并发排队、按次
权限、报告文件。你定了前三样不要，理由只剩报告文件一样，而它改成“最小配合”就能
解决。剩下的都是自己维护一套派发引擎的代价：

- 每次后台派发完成，父会话被叫醒两轮——宿主一条、插件补发一条（沙箱实测）；
- 重启后的收养重叠：宿主会按作业的恢复记录把子会话续跑起来（源码；沙箱未实测）；
- 两套规矩：原生派发不经过插件的派发门（沙箱实测，原缺陷 F2）；
- 今天的 `/forge stop` 看不见原生派出的子代理：两个原生子代理正在忙时调它，回的是
  “本会话没有在飞的派发，没什么可停的”（沙箱实测）。

而且真机上这已经是既成事实：11-24 那起“会话认错目录”的事故，形状就是 forge 会话
经原生 `subagent` 派出子会话（change #1；复现臂驱动 `repro-anchor-lastinit.mjs` 的
注释所记）。D 做的是让插件的约定跟上实际在用的那条路。

**原生路是通的：**

| 事实 | 出处 |
| --- | --- |
| 真机的 forge 会话能调通原生 `subagent`：派发 → 子会话执行 → 完成通知回主会话（宿主 2.4.0，模型 `glm-5.4`） | 真机实调：2026-11-24T20:30Z（UTC），`agent=general`，建出子会话、回了话、通知送达 |
| 沙箱里能用原生 `subagent` 派出 forge 工人（并因此绕过插件的分区门） | 沙箱实测，见状态页“缺陷 F2” |
| 原生 `subagent` 无条件内建登记，`codemode: false`（不在代码模式的目录里） | 源码 |
| 带 `sessionID` 就续用同一个子会话（它必须是当前会话的孩子） | 源码；沙箱实测是通的（续用的是同一个子会话，孩子答得上第二句）。社区那条“续用总是报找不到”的开放 issue（宿主 #59293）在沙箱里没有复现 |
| 总是后台运行；默认不能再派下级（`experimental.subagent_depth` 默认 1） | 源码；沙箱实测：子会话再派被上限挡住，报错原文明确 |
| 父会话收得到孩子的取消和异常结束通知，并且会被叫醒 | 沙箱实测。原先写的是收不到，那是读错了宿主的一条注释，已更正 |
| 原生派出的子会话落在父会话的目录里 | 沙箱实测，3 次 |
| 孩子收工后留在宿主那边的后台命令，从插件这边终止得了（走宿主一组不属于实验性的接口） | 源码；沙箱实测 3 次，见 design 的 Verification ⑧ |

## What Changes

1. **v2 入口的派发面换成宿主原生的 `subagent`。** 插件不再把自己那套引擎作为 v2 上
   的派发面提供给模型；执行、完成通知、重启后的续跑都由宿主管。
2. **`/forge stop` 能停掉本会话的原生子代理，连它们留在宿主那边的后台命令一起。**
   做法：先终止命令，紧接着打断，回访几轮，最后取消插件自己的作业。顺序是沙箱里
   试出来的，原因见 design 的 D4。
3. **保留：** forge-\* 工人的代理预设（模型、工具面、只读封印，仍由插件编译，
   `src/roster-compile.ts`；另加一条“工人不能提问”的封印，见 D6）；plan / goal /
   crew 三个 harness 需要的最小配合逻辑。
4. **两条保险：** v1 入口原样不动；留一个配置开关，可以切回 `task` 引擎。

## 不做的

- 不做同步派发、并发上限加排队、按次下发的权限（“不许提问”这类只写进代理定义）。
- 不自己封装“主代理读子代理”“给子代理再发消息”，交给宿主。
- 不给原生派发加派发门（change #2 已撤）。
- 不动 v1 入口。

## 需要你拍板的六件事

D 的方向你已经定了。下面六件是落地时的具体选择，我先各选了一个默认项，理由在
design 的“决定”一节。批准这份 change，就等于按默认项走；想改哪条，告诉我编号。

| | 题目 | 我先选的默认项 |
| --- | --- | --- |
| D1 | 开关的默认值与保留多久 | v2 上默认走原生；开关保留一版实机观察后再议删除 |
| D2 | 插件的 `task` 在 v2 上怎么处置 | 不再登记给模型（代码留着，开关切回时才登记） |
| D3 | 派发日志和报告文件在原生路上还要不要 | 留一份最小的“本会话子代理记录”，供 crew 的摘要和 `/forge stop` 用；报告文件不再生成 |
| D4 | `/forge stop` 怎么停。要不要为“终止孩子留在宿主那边的后台命令”走宿主的 HTTP 接口——插件接口里没有这项；上一版在这里写的是“接受一小块停不干净”，已改 | 走：先终止命令，紧接着打断，回访几轮，最后取消插件自己的作业；子会话保留。沙箱实测这样停得干净。“把子会话整个删掉”默认不用 |
| D5 | 草稿期禁止派发这条规则，在原生路上保不保留 | 保留。它现在不拦原生 `subagent`（沙箱实测），要新加一条判定 |
| D6 | 工人在原生路上不能提问 | 把“不提问”的封印写进工人代理文件，只在 v2 上加 |

## 沙箱验证的结果

动工前要在沙箱里验的几件都跑完了（UTC 2026-11-24 22:49–23:44，宿主 2.4.0），逐项的
结果在 design 的 Verification 一节。草案照实测改了这些地方：

- 续用：原来没验，现在实测是通的，社区那条 issue 没有复现。
- 通知：孩子被取消以后，父会话照样收得到通知、会被叫醒。原先写的是收不到，那是
  我把宿主的一条注释读错了。
- `/forge stop`：要先打断、后取消插件自己的作业，顺序反过来工人会“报假完成”。
- `/forge stop` 补测（对照同行之后）：孩子收工后留在宿主那边的后台命令**终止得了**。
  只终止命令不够——孩子会被叫醒再答一轮，父会话收到“已完成”；终止之后紧接着打断，
  孩子记为被打断，父会话收到“已取消”。所以上一版的“接受一小块停不干净”改成了
  “连命令一起终止”。
- 草稿期禁令：现在不拦原生派发，要新加判定（原来以为只要保留）。
- “只打断够不着正在跑的命令”：服务端的打断停得掉孩子回合里的前台命令；停不掉的
  是已收工的孩子留下的后台作业。

探针过程中另外发现两件草案里原来没有的事：工人原生派出去以后一提问就没人答、一直
挂着（所以多了 D6）；工人代理文件的描述还写着“用 task 工具派发”，换路后要改。

还照你的要求读了十来个支持 v2 的编排插件的源码，逐条对照了这六件：五件的默认项都有
先例，或者同行没有对应物，没动；D4 因为上面的补测改了；另有三处是我上一版写错、读错
的，已更正。谁怎么做、采纳了什么、没采纳什么，都在 design 的“对照同行之后改了什么”
一节，取材清单在 design 文末。

还有几件没验（真实的上游超时、同时停多个孩子等），清单在 design 的 Verification
末尾，动工时补。

## Impact

- 规格：`forge-subagents`（本 change 的 delta）；`crew-harness` 里“子任务以并行的
  `task` 调用成波执行”这句要改，补它的 delta；动到 `/forge stop` 的现有场景时一并补。

  派发记录的地方。v1 入口不动。
- 版本：这是行为改动，建议发 0.35.0（不挤进 0.34.x）。
- 文档：README 的派发章节、架构文档。
