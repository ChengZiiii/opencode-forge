# forge-agent Specification

## Purpose
Govern the single general-purpose agent identity for opencode sessions: register forge, hide the native build/plan agents at runtime for the plugin's lifetime, provide a one-knob return-to-native and uninstall self-healing — replacing "multi-agent persona switching" as the orchestration shape.

## Requirements

### Requirement: One-knob return to native

The plugin SHALL rely on the v2 host's native plugin enable/disable mechanism as the single switch for its runtime contribution. Disabling the plugin and restarting the host SHALL remove Forge runtime registrations, agent injection and picker/default transforms, tool and permission hooks, harness tools and commands, continuation behavior, and builtin search overrides. The host's own configuration and agent definitions SHALL remain authoritative. An agent-level disable setting for `forge` SHALL NOT be treated as a whole-plugin off switch. Forge SHALL NOT maintain a parallel plugin-wide disable knob or modify user configuration to implement this behavior.

Generated native agent Markdown files have a separate host-managed lifetime; disabling the plugin SHALL NOT remove or rewrite these files. Namespaced workers and generated `general`/`explore` overrides left on a host agent search path may remain registered independently of the plugin, without its runtime gates or injections. The README SHALL disclose this boundary and explain the explicit artifact management and recovery steps in 'Uninstall self-healing'.

#### Scenario: Native restored after the knob is set

- **WHEN** the user disables Forge using the host's native plugin disable mechanism and restarts opencode
- **THEN** Forge contributes no runtime agent registrations, transforms, search overrides, hooks, harness tools, commands or continuation behavior; the host/user agent and tool definitions determine the resulting registry, including independently loaded Markdown files, if any

#### Scenario: Agent disable does not disable the plugin

- **WHEN** the user disables only the `forge` agent in host configuration while Forge remains enabled
- **THEN** that agent follows the host's agent configuration semantics, and the plugin's runtime contributions remain enabled

#### Scenario: Re-enabling restores runtime contributions

- **WHEN** the user reverses the native plugin disable setting and restarts the host
- **THEN** Forge setup and its runtime surfaces return subject to normal host configuration and existing recipe/content compatibility and authorized sync rules; files were not deleted or rewritten by the disable/enable switch itself

### Requirement: Uninstall self-healing

Uninstalling or disabling Forge SHALL remove its runtime contributions without modifying user configuration, hand-written agent definitions, generated Markdown, recipes or historical plan/goal/crew data by itself. The README SHALL distinguish plugin removal from explicit user management of separately loaded generated definitions, and SHALL document the actual workspace and global agent directories (including configured global directory overrides), namespaced worker filenames and generated `general.md` / `explore.md` overrides, how to verify ownership by the in-content `<!-- GENERATED BY forge_sync` marker and corresponding filename, and how the user can back up and move confirmed generated files out of host scan paths or remove them individually, then reload/restart. It SHALL explicitly warn against prefix-only or wildcard removal, preserve unmarked/unknown and hand-written same-name files, and explain restoring backups or authorized sync after re-enable. User-authored config such as an explicit default agent or hidden flags SHALL remain under user control; returning to native-only behavior requires the user to review those settings and separately loaded artifacts.

#### Scenario: Native restored after uninstall

- **WHEN** the user uninstalls the plugin following the README, explicitly manages any confirmed generated agent files and plugin-specific user config as desired, and restarts opencode
- **THEN** Forge runtime contributions are absent, the host/user configuration governs native visibility and the default agent, builtin search is restored, and any remaining independently loaded agent files retain their normal host semantics

#### Scenario: Uninstall keeps plan data

- **WHEN** the workspace contains historical plan, goal or crew files or recipes and the user uninstalls the plugin
- **THEN** these files and directories remain untouched

#### Scenario: Generated and handwritten definitions are managed separately

- **WHEN** the host loads workspace/global Forge-generated worker files, generated built-in overrides and hand-written agent definitions and the user disables or uninstalls Forge
- **THEN** the files remain byte-identical by virtue of the plugin transition alone; the documented explicit cleanup identifies only marker-confirmed generated files, never treating a filename alone as ownership, and after those files are moved or removed and the host reloaded, handwritten definitions remain in effect

### Requirement: v2 forward-compatible registration

The plugin `SHALL` provide its whole surface through the `setup` entry —
the package's only entry point ('Single v2 entry point'). `setup` SHALL initialize the retained models-dev catalog through its existing snapshot/cache loading and null fallback before depth selection uses it; catalog-backed and fallback behavior SHALL be verified via actual setup, not test injection. `setup` `SHALL`
register: the forge primary agent; the workers through the complete
sole-pool-ownership resolver (not a simplified single-workspace subset) —
compiled native agent files by default, or a runtime agent-draft projection
on a create-only basis where the `materialize` escape hatch is opted into
(an existing target entry is skipped; fields use the v2 shape; forge-subagents
'Materialization as native subagents with a pinned model'); the harness tool
surface (plan_\*, goal_\*, crew_\*, `forge_sync`) via `ctx.tool.transform`
with JSON Schema argument contracts, and the search override on the builtin
`grep` / `glob` tools through the same editor's update; the belts — the permission belt (draft write-freeze, the
dispatch gates on native `subagent` calls, plan/goal/crew double gates,
worker→STATE primary-only refusals, status-file boundaries) via
`ctx.permission.hook("evaluate")` for the outcomes it rewrites or denies
without a session lookup and via `ctx.tool.hook("execute.before")` for the
gates that read the session's own record (a rejection there refuses the call
before the tool runs), with gate rewrites producing ask outcomes so user
dialogs remain the gates; the session seams via
`ctx.tool.hook("execute.after")` (activity marking) and
`ctx.session.hook("prompt")` / `ctx.session.hook("context")` /
`ctx.session.hook("compaction")` (family mapping capture, thoughtLevel
injection, forge system injections, goal-brief compaction reinjection); the
`/plan` `/goal` `/crew` `/forge` commands via the command domain (the
`/forge` command running its `stop` route in its own execution); and the
continuation engines (goal idle continuation, crew idle continuation,
`session.deleted` cleanup) via `ctx.event.subscribe()` and the session idle
hook, each with the cleanup function. On host API shape
drift, registration `SHALL` skip silently instead of throwing; a domain
that is absent or reshaped disables exactly its own feature slice and the
rest of `setup` still runs.

Pool and workspace anchor resolution `SHALL` accept anchor fields in BOTH
shapes: a zero-arg function (invoked for the value, unchanged) or a plain
property value used directly as the anchor string. A non-callable anchor
field `SHALL NOT` be treated as absent: on the 2.3.2 host, where
`ctx.location.directory` is a string property and `ctx.location.worktree`
does not exist, anchor resolution `SHALL` still produce candidates from
the property so the `forge-<ns>-<id>` workers materialize. Guarded
degradation `SHALL NOT` swallow the entire pool when only the anchor
field's shape differs from the function expectation.

#### Scenario: An existing same-name entry is not clobbered under v2

- **WHEN** the host calls `setup` and the agent draft already contains a
  `forge` entry
- **THEN** the plugin skips creation and the existing entry's content is
  unchanged

#### Scenario: The full tool surface registers under v2

- **WHEN** a host with `ctx.tool.transform` loads the plugin
- **THEN** the harness tools (plan_\*, goal_\*, crew_\*, `forge_sync`) appear
  in the tool registry with their argument contracts, `grep` and `glob`
  appear once each carrying the plugin's override, and no plugin exec or
  dispatch tool is registered

#### Scenario: Permission gates fire under v2

- **WHEN** a plan draft is active and a write-class tool call (the builtin
  `shell` included) or a native `subagent` call is evaluated
- **THEN** the call is refused (or an ask rewrite is produced for the gated
  plan/goal/crew transitions) by whichever belt decides it first

#### Scenario: Shape drift disables only its own slice

- **WHEN** a v2 host lacks `ctx.permission` (or its method shapes drifted)
  while the other domains are intact
- **THEN** the permission belt registration is skipped without throwing
  and the tool, agent, session, command, and event registrations still run

#### Scenario: Property-shaped location anchors resolve on real v2 hosts

- **WHEN** a v2 host exposes `ctx.location.directory` as a plain string
  property (opencode 2.3.2 field reality) and a workspace pool declares
  anchor-based workers
- **THEN** the resolver reads the property value directly, materializes
  the `forge-<ns>-<id>` workers for the pool, and `/api/agent` lists them
  for the pool's directory

#### Scenario: Absent anchor fields fall through without failing

- **WHEN** the host context lacks an anchor field entirely (e.g.
  `ctx.location.worktree` does not exist on 2.3.2)
- **THEN** that field yields no candidate, resolution falls through to the
  remaining candidates, and no error is thrown

### Requirement: v2 single-agent surface

With hiding enabled and subject to explicit user configuration, the plugin SHALL suppress the native `build` and `plan` primary agents by setting `hidden: true` on their agent records via the agent domain — records are hidden, never removed, and no other field of a native record SHALL be touched. The suppression and default-setting SHALL be delivered exclusively as runtime agent-layer state and SHALL NOT write to the user's opencode config or any file outside the plugin's own config domain (forge.json); removing the plugin SHALL restore the host/user-configured visibility and default subject on the next agent-layer rebuild. The suppression SHALL be guarded (an absent record is skipped, an already-hidden record is left untouched), fail-soft per record, and SHALL be opt-out-able via `"hideNativeAgents": false` in the global forge.json layer. The host's native plugin disable mechanism is the whole-plugin runtime off switch ('One-knob return to native'); agent-level disablement is independent. Where the agent draft editor exposes a default setter AND the plugin's transforms are confirmed to run before the host's config→agent merge (so an explicit user `default_agent` overrides the plugin), `setup` SHALL set the agent default to `forge`; on hosts where that ordering cannot be confirmed, the default-subject slice SHALL ship nothing and the README config recipe (`default_agent: "forge"`) remains the documented way. Suppression SHALL NOT touch the `general`, `explore`, `compaction`, `title`, or `summary` agents.

#### Scenario: Native primaries disappear from the picker on v2

- **WHEN** the plugin loads on a v2 host, hiding is enabled, and no explicit user setting overrides it
- **THEN** the native `build` and `plan` records carry `hidden: true` and the agent picker offers `forge` as the visible primary, while `general`/`explore`/host-internal agents remain untouched

#### Scenario: Uninstalling the plugin restores the natives

- **WHEN** the plugin is removed and the agent layer rebuilds
- **THEN** the plugin’s hiding and default transform are removed; host/user configuration decides visibility and default — no trace of the suppression persists in the user's config or on disk

#### Scenario: Nothing is written to the user's config

- **WHEN** the plugin delivers suppression or default-setting
- **THEN** the user's opencode config file is byte-identical to before the plugin loaded; all plugin-owned state is runtime agent-layer data or files in the plugin's own domain (forge.json, plugin ledgers)

#### Scenario: Existing native-agent sessions keep working

- **WHEN** a session was created with agent `build` before suppression and is reopened after it
- **THEN** the session still resolves its agent (hidden, not removed) and behaves exactly as before

#### Scenario: The opt-out knob restores the natives

- **WHEN** the global forge.json sets `"hideNativeAgents": false`
- **THEN** `setup` leaves the native `build`/`plan` records untouched and picker visibility follows the host and user config

#### Scenario: A user's explicit config still wins where ordering allows

- **WHEN** the host merges user config agent entries after plugin transforms (2.3.2 observed ordering) and the user explicitly sets `agent.build.hidden: false`
- **THEN** the final merged record is visible — the plugin's suppression never overrides an explicit user statement on hosts with that ordering

#### Scenario: Fresh sessions default to forge under the confirmed ordering

- **WHEN** the agent draft editor exposes a default setter, the plugin-before-config ordering is confirmed, and the user has no explicit `default_agent`
- **THEN** a new session without a named agent starts as `forge`

### Requirement: Every user-confirmation door raises its dialog under v2

On a v2 host the permission belt SHALL rewrite the evaluate outcome of every user-confirmation door — `plan_approve`, `goal_write`, `goal_complete`, `goal_resume`, `goal_discard` and `crew_close` — to `ask` unless the outcome is `deny`, so that the gate each of these tools opens is a real pending dialog that the user's answer settles. The belt SHALL leave the outcome of a tool that is not a door (for example `crew_begin`) exactly as the host produced it. A door the tool itself does not open produces no evaluation and no dialog: both `crew_close` paths stay ask-free while a live active goal governs the session, as the crew-harness spec requires.

On a host that has initialized the plugin in more than one directory, a door opened in a session SHALL raise its dialog for that session whether or not the session's directory is the most recently initialized one: the plugin SHALL route the ask through the host interface captured by the plugin initialization of the session's own directory — the initialization that registered the tool being called — never through an interface captured for another directory or by the latest initialization, and SHALL keep no module-level interface that a door could fall back to. A pending dialog raised this way SHALL be visible to the session's terminal client and answerable from it — the request SHALL sit in the pending table that the session's own routes read — and SHALL settle on the user's answer or, if the watchdog is enabled, fail-closed on the bounded timeout in gate-asks (0 disables the plugin timeout). When the interface captured for the most recently initialized directory is no longer usable because that directory left the host, doors in the other directories SHALL keep working; a door that cannot raise its dialog SHALL fail closed with a clear error and SHALL never execute without the user's answer. The plugin SHALL NOT retry a failed ask on another directory's interface: a refusal and a closed directory are indistinguishable, and the user's refusal is final.

#### Scenario: crew_close asks in a session no goal governs

- **WHEN** `crew_close` (either close path) is evaluated with outcome `allow` on a v2 host, in a session that no live active goal governs
- **THEN** the evaluate outcome is `ask`, and the close does not execute until the user answers the dialog

#### Scenario: crew_close stays ask-free under a governing goal

- **WHEN** a live active goal governs the session and `crew_close` is called on either path
- **THEN** no dialog is raised and the close executes, exactly as before

#### Scenario: A tool that is not a door is untouched

- **WHEN** `crew_begin` is evaluated on a v2 host
- **THEN** the belt leaves the outcome as the host produced it

#### Scenario: An explicit deny is kept

- **WHEN** a door is evaluated with outcome `deny`
- **THEN** the belt leaves it `deny` and the tool is refused without a dialog

#### Scenario: A door in a session whose directory is not the last initialized one

- **WHEN** the host initialized the plugin in directory A and afterwards in directory B, and a door is opened in a session bound to A
- **THEN** the request sits in A's pending table, where that session's terminal client both sees and answers it, the terminal's answer reaches the request, and the door executes only after that answer

#### Scenario: The most recently initialized directory leaves the host

- **WHEN** directory B, initialized after A, is evicted from the host, and afterwards a door is opened in a session bound to A
- **THEN** the dialog is raised and the door settles on the user's answer

#### Scenario: The evicted directory comes back

- **WHEN** directory B is evicted and later booted again, so it is once more the most recently initialized one, and a door is opened in a session bound to A
- **THEN** the dialog is raised for that session and never lands in B

#### Scenario: The host gave an initialization no permission interface

- **WHEN** the plugin's initialization for a directory captured no permission interface from the host, and a door is called in a session of that directory
- **THEN** the call is refused with an error that says it was refused fail-closed, and nothing is executed

### Requirement: Register the forge primary agent on the host's builtin shell

Once the plugin loads, the system SHALL register a primary general-purpose agent with id `forge` (full read/write/execute tool surface). The native primary records remain available to existing sessions; Tab visibility and default agent follow the configurable `v2 single-agent surface` requirement, not record availability. Set forge as default only on probe-confirmed ordering where explicit user config wins; otherwise leave default unchanged.

The forge agent's execute surface SHALL be the host's builtin shell tool: the plugin SHALL NOT hide it, SHALL register no exec tool of its own, and SHALL NOT of its own accord push a deny of it onto the forge agent record or a worker's compiled face — a deny the user's config or a worker's recipe states explicitly is theirs and stands as written, and the plan draft's session-scoped write ban (plan-harness 'Hard write ban during draft') reaches the forge agent like every other. A user-defined `forge` agent entry SHALL keep every field it has; no option SHALL exist that hides the builtin shell or restores a plugin exec surface. The plugin SHALL push no shell mandate into any prompt: where a command runs is between the model and the host.

#### Scenario: forge appears in the agent list after an official install

- **WHEN** the plugin is installed via an official `opencode plugin` install mode and loaded, and the user views the agent list
- **THEN** the list contains `forge` as a primary general-purpose agent

#### Scenario: A direct unplanned task is executed by forge

- **WHEN** the user issues an implementation-type task directly in a forge session (without `/plan`)
- **THEN** forge executes the task directly, with no agent switching at any point

#### Scenario: A fresh session defaults to forge under coexistence

- **WHEN** the plugin is loaded and the user starts a session without naming an agent (bare `opencode run` or a new TUI session with no remembered choice)
- **THEN** where the setter and merge ordering are probe-confirmed, forge is default unless the user configured `default_agent`; otherwise no default is set by the plugin

#### Scenario: The exec surface is the builtin shell regardless of native capability

- **WHEN** the host's builtin shell offers a native background parameter and the user's config leaves the forge agent's shell open
- **THEN** the forge agent's toolset includes the builtin shell tool, its record carries no plugin-pushed deny of it, and no plugin exec tool is registered

#### Scenario: A user-defined forge entry keeps its fields

- **WHEN** the user has their own `agent["forge"]` configuration
- **THEN** the plugin adds no tools merge and no shell deny to that entry, and its builtin shell stays available as the entry's own configuration leaves it

#### Scenario: No forge-authored shell mandate reaches a prompt

- **WHEN** any session builds its system prompt
- **THEN** no forge-authored text names a plugin exec tool or tells the model that the builtin shell is refused

### Requirement: Single v2 entry point

The package SHALL expose one plugin entry: the default export whose `setup` registers everything ('v2 forward-compatible registration'). The v1 `server` entry and its `./server` export SHALL NOT exist, and the package metadata SHALL declare host generation 2 as the only supported host — in the host engine range and in the README's install requirements. Nothing SHALL be kept alive for an earlier host generation: every behavior the plugin offers SHALL come from `setup`, and a capability retired for the plugin as a whole SHALL be gone from the package entirely.

#### Scenario: The package has no v1 entry

- **WHEN** the published package's entry points and metadata are inspected
- **THEN** the default export carries `setup` and no `server`, the exports map has no `./server` key, and the host engine range names generation 2 only

#### Scenario: Every surface arrives through setup

- **WHEN** a supported host loads the plugin
- **THEN** the forge primary agent, the worker definitions, the harness tools, the search override, the belts, the commands, and the continuation engines are all registered by the one `setup` call

#### Scenario: An earlier-generation host is out of range

- **WHEN** the package's supported-host declaration is read
- **THEN** it names generation 2 only, and the README says so
