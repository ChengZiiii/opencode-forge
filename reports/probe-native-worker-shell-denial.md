## 4. 宿主机制逆向（exe ASCII 扫描，offset 为命中位置）

### 4.1 逐字文案的唯一来源（offset 182803242–182803673，Permission 模块）

```
var oA=[{action:"*",resource:"*",effect:"deny"}]                       // DENY_ALL 兜底规则
class QS extends …("Permission.BlockedError",{rules,permission,resources,reason}) {
  get message(){ return this.reason ?? `Permission denied: ${this.permission}` }
}
```

**`Permission denied: <action>` 只在 BlockedError 且 reason 为空时出现**。而 assert 的规则装配（同模块）：

```
G = async (sessionID, agentOverride) => {
  const session = await sessions.get(sessionID); if (!session) throw …
  const agentRecord = await agents.resolve(agentOverride ?? session.agent)   // ← 域敏感
  return concat(agentRecord?.permissions ?? oA, session.permissions ?? [])  // ← 解析失败 = oA 全拒
}
// 命中 effect:"deny" 规则 → BlockedError(reason 空) → 逐字文案；无匹配规则 → 默认 {effect:"ask"}
```

结论：在 session permission 为空、config 无 permission 段、saved rules 只有 allow 的生产环境里，**唯一能产生 deny 的来源是 `agents.resolve()` 在断言域解析不到会话的 agent → 落 `oA` 全拒**。deny 命中不产生 ask——与生产"零 ask"吻合。

### 4.2 directory 钳制（API 层）

- `POST /api/session` 的 body/query `directory` **一律钳制到 serve root**（A11.1：三次显式 `directory:<ws>` 全部落 `<T>/A`）。
- SDK v2 client 把 `x-opencode-directory` header：POST 保留 header、GET/HEAD 重写为 `?directory=`（sdk dist v2/client.js 逐字）——GET 层解析（`/api/agent?directory=`）有效（A9.2 亲证 w1 可见），但对会话创建的锚定无效。
- v2 面 `/session` POST 在本宿主 405（probe-v2-session.mjs）——raw HTTP 无法在 serve root 之下锚定会话。
- `--service` 模式：会话锚定 home（A8.2 亲证 dir=`<T>/A/home`），且不打密码行（§0.2）。
- 生产 TUI/桌面客户端在进程内携带工作区 directory 上下文——**这是 raw HTTP 复现不了生产几何的原因**。

## 7. 判决

### 7.1 根因（定性，证据链闭合）

**分层解析错位（scope split）× 0.30.0 的 ask→assert 桥。**

1. 生产 serve root=home；工人只以 md 形式存在于 `<ws>/.opencode/agent/`（0.30.0 的 native 物化）；home 层 agent 目录为空、无全局池 → 插件（锚 home）从不注册工人程序化记录。
2. 工人会话的 Code Mode 运行时锚在 home（§2.3 生产亲证：glob 相对路径解析到 `C:\Users\Soren`）。
3. 0.30.0 把 shell 门禁的 `ctx.ask` 桥接为 `ctx.permission.assert({sessionID, agent, action:"forge_shell"})`（§5.3）。
4. 宿主断言在**插件域**做 `agents.resolve("forge-plugindev-spec-reviewer")` → home 层无此 md → 解析失败 → 落 `oA`（`[{action:"*",resource:"*",effect:"deny"}]`）→ BlockedError(reason 空) → **逐字 `Permission denied: forge_shell`**（§4.1 公式逐字推出）。
5. 零 ask / session permission 空 / config 无 permission 段 / saved rules 0——全部与"deny 规则命中不产生 ask、且唯一 deny 源是 oA 兜底"自洽。
6. 每工具分裂：只有 `forge_shell`/`forge_jobs` 过门禁，`forge_grep`/`forge_glob` 无门禁（§5.2）。
7. 父会话（`forge`）是插件程序化注册的全局 agent → 断言域可解析 → 其 permission 映射仅 `task:"deny"` → shell 放行。与"父会话能跑 shell"吻合。
8. 0.29.x 无此回归：ask 走宿主原生询问面（v1 工具 ctx 自带 ask，桥不激活），shell 执行不依赖"断言域的 agent 解析"。

### 7.2 修复通道

1. **插件侧（正解，任一即可）**：
   - `forgeShellGate` 不走 `ctx.permission.assert`（宿主工具 ctx 无 ask 时降级为直接放行——readonly seal 与 job 只读兜底已存在），或
   - 断言前显式解析目标 agent 并传入 rules / 以会话 directory 域解析，或
   - 工人在 native 物化之外同时程序化注册（保证断言域可解析）。
2. **宿主侧（建议上报上游）**：`Permission.assert` 的 agent 解析应使用**会话的 directory 域**而非插件/断言调用方域；且 resolve 失败回退全拒时应携带可诊断信号（目前对用户只表现为一条逐字文案，无 ask、无规则痕迹）。
3. **用户侧短期缓解**：把工人 md 复制一份到 `~/.config/opencode/agent/`（home 层）→ 断言域可解析 → `oA` 不触发。代价：agent 全局面污染（所有项目的 TUI 选择器都会看到）。机制成立（§4.1/§5.1 直接推论），但**未端到端验证**——沙盒无法复现生产几何（§6）。
